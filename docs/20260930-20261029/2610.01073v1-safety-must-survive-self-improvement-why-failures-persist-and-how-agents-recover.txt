ABSTRACT 

Recursive self-improvement (RSI) allows agents to carry useful changes across generations. Maintaining safety across these generations involves both preventing unsafe behavior from persisting and enabling recovery when failures occur. We study these challenges through a controlled testbed of stateful authorization tasks, where fixed LLM editors optimize executable agent components and independent traces record their effects. Paired interventions separate which revisions pass validation, which program continues running, and which program the editor revises next. After a new authorization dependency invalidates previously tested optimizations, historical scores preserve the same unsafe programs in 22 of 48 framework histories despite a correct alternative in every affected archive. Refreshing scores restores correctness on the original suite, with residual failures on independently composed tests. Failures also persist under an unchanged contract when all proposals are rejected and the failed incumbent remains active. Starting from shared failures, editing the initial implementation instead of the failed one improves recovery, although the advantage varies across editors. Full validation and validated rollback end with fully correct programs in the core trajectory study while retaining over 43% deployment savings. Preserving agent safety requires checking what will run under current conditions and choosing which implementation to edit next.

These changes can operate through memory, tools, and workflows as well as model parameters (Gao et al., 2025, Fang et al., 2025). If the service later introduces delegated permission, upstream revocation can invalidate authorization without changing that local version. The optimized agent continues acting, while the initial program remains correct because it checks effective permission on every request (Fig. 1a). We investigate these mechanisms in a controlled testbed covering session authorization, filesystem containment, tool approval, and structured user consent. Fixed LLM editors repeatedly optimize executable agent components while selected programs and their histories evolve. Independent traces distinguish unauthorized effects from completion of permitted work, so blanket refusal cannot count as successful repair. Following every generation reveals failure entry, persistence, and recovery. Three matched comparisons separate repair availability from the decisions that govern its use (Fig. 1c). First, we compare historical and current readouts of the same archive. A separate refresh intervention updates stored scores, feedback, and selection metadata before search resumes. Second, we hold the incumbent, proposals, and test outcomes fixed while varying retention after rejection. Third, we start from the same failed programs and vary the editing source while holding validation and retention fixed. Using the founder as the editing source does not automatically deploy it. These controls separate generating a repair from protecting execution during repair. Full initial validation does not prevent later failure under new authorization dependen-cies. Editing the initial implementation improves recovery from shared failures relative to editing the failed version, with the advantage varying across editors. In the core trajectory study, full validation and validated rollback each achieve fully correct endpoints with mean deployment service-cost savings above 43%, excluding validation expenditure. Thus, execution and editing decisions jointly determine whether useful improvements preserve safety across generations. Our contributions are threefold:

3.1 Setup 

Our stateful tasks cover session authorization, filesystem containment, tool approval, and structured user consent. Event streams interleave requests with changes in permission or environment state. Public tests determine eligibility and feedback, audit tests support rollback, and hidden tests measure outcomes. The core public, audit, and hidden suites contain different instances of known test categories. The new-dependency studies introduce authorization mechanisms absent from all initial suites. Fixed editors receive efficiency or maintenance objectives under the same full contract, requesting lower service cost or clearer implementation, respectively. Paired branches share starting programs and workloads. Statistical comparisons resample starting blocks rather than generations. Table 1 maps the controlled comparisons, and Appendix A.1 specifies dataset construction and splits. 

3.2 New Authorization Dependencies 

We first ask whether a program can become unsafe after passing every initial condition. Qwen3 Coder, Claude Sonnet 4.5 (Sonnet), and GPT-5.6 Sol (GPT) optimize two stateful authorization tasks under full initial validation, producing 72 histories. After four genera-tions, a previously absent dependency makes permission depend on an upstream grant or resource classification without changing the meaning of token-local version queries. Neither mechanism appears in any public, audit, or hidden suite before this reveal. All strategies receive the new contract and expanded tests simultaneously. They then continue from the same checkpoint under different editing, retention, and archive-eligibility rules. The dependencies, reveal time, and strategies were fixed before the pilot, with additional seeds run under the same protocol (Appendix B). The new dependency exposes unsafe behavior in 22 of 24 GPT checkpoints despite their initial validation, while every frozen founder remains fully correct. Sonnet checkpoints instead tend to miss permitted work, and Qwen’s remain correct. The frozen founder faces the same changed environment without inheriting the optimization and still completes the task correctly. The new condition therefore breaks an assumption used by the optimized program while leaving a correct implementation available. Ordinary incumbent editing repairs the unsafe checkpoints promptly, whereas historical archive selection preserves them throughout the continuation (Fig. 2a,b). Thus the change exposes a repairable failure, and the selection rule determines whether that failure persists.

3.3 Persistence through Historical Scores 

We next test whether an available repair is selected within existing search components. The study uses OpenEvolve’s controller and database (Sharma, 2025), together with unchanged DGM (Zhang et al., 2025a) functions for parent sampling, archive updates, and original scores. Our authorization evaluator is integrated with these pinned upstream components, preserving their archive and selection behavior. GPT and Sonnet optimize both authorization mechanisms across 48 histories, with the new dependency revealed after eight fully validated iterations. A readout chooses a program from an archive. Historical and current readouts rank the same stored programs using recorded evaluations or current tests, isolating selection without changing search. A separate score refresh intervention updates stored scores, feed-back, and selection metadata before continuing evolution. Matched continuations compare refresh with historical scores under the same editing budget. The readout comparison tests whether selection overlooks a correct program already in the archive. Continuing the search with or without refreshed scores then tests whether updating the evaluations improves subsequent selections under the same editing budget. Historical readout retains the same 22 unsafe programs through iteration 100, all in GPT histories, although every affected archive contains a correct alternative. Current readout selects fully correct programs on the original suite, and score refresh keeps the matched continuation correct throughout (Fig. 2c and Table 3). A recorded DGM delegation case explains the mechanism: a local-version cache remains highly ranked after upstream revocation, while correct later revisions are already available. Refresh replaces the failed program with an existing repair before the editor generates any new code. Later edits also receive feedback from the updated tests. Independent compositions, kept out of prompts and selection, confirm gains in safety and useful completion while revealing errors missed by the original suite (Fig. 2d). These residual failures show that refreshing eligibility and expanding test coverage serve complementary purposes. 3.4 Persistence after Rejection 

Current validation can detect a failure without ending its execution. Under the keep rule, an empty eligible set returns the incumbent (Equation 1). We isolate this decision under an unchanged contract by giving keep and founder fallback the same failed incumbent, two GPT or Sonnet proposals, and test outcomes. Whenever all candidates fail, keep leaves the unsafe incumbent active, whereas fallback restores the correct founder (Fig. 3b). Because this comparison precedes any divergence in subsequent edits, the deployment difference is attributable to fallback alone. A complementary analysis freezes 432 candidate pools, costs, and outcomes while varying validation coverage. At full coverage, the remaining safety gap comes entirely from pools without a passing program: keep retains the failed incumbent, while founder fallback remains correct (Fig. 3a). These unsafe pools come from a small number of Qwen lineages. The identical-proposal comparison shows the same keep-versus-fallback difference with both GPT and Sonnet. Complete-history audits likewise confirm repeated retention of unchanged failed code after all candidates are rejected, most often with Qwen. Thus broader detection and better candidate generation leave a separate obligation to specify safe behavior when no proposal passes. The code-identity audit and recorded histories appear in Appendices D.2 and F.

3.6 Safety and Utility 

We finally ask whether preserving safety still permits useful optimization. The core study follows correct founders for 12 generations across four task families, the same three original editors, two version-query costs, and 12 seeds, yielding 288 matched blocks. Eight conditions vary editing objective, source, validation, and retention. Routine validation expands to the full public suite at generation 4, while preservation controls use full validation from the start, validated rollback, or an execution guard. We measure safety through independent hidden effects and utility through full correctness and founder-relative service-cost savings. Founders already complete permitted tasks correctly, so useful improvement means reducing the service cost of that work. This separates efficiency gains from simply skipping actions or checks. Consent shows the largest persistence contrast. Safety initially falls under both inherited and founder editing, then recovers much more strongly with founder editing after validation expands (Fig. 5a). Both conditions encounter failures in similar numbers of lineages, but fewer remain unsafe with founder editing. Founder editing also has higher final safety for each original editor. Unlike the shared-root experiment, these trajectories begin with correct programs and allow each condition to generate its own failures. They therefore describe

how often errors enter and remain in the selected histories. The shared-root comparison then isolates recovery from exactly the same failed program, resolving an ambiguity that the natural trajectories alone cannot. Approval shows a smaller effect, while session and filesystem failures are rare. The task and editor breakdowns and paired estimates appear in Appendix E. Validated rollback and full validation finish with fully correct endpoints while retaining mean service-cost savings above 43% (Fig. 5b). The founder at zero savings and full correctness makes the benefit of continued optimization explicit. An execution guard also prevents unauthorized effects, but evolved programs can still miss permitted work, explaining why safety and full correctness must be measured separately. Validation itself consumes resources, so the deployment savings should be read together with how often each selected program is used. Repeated use amortizes the cost of checking, while short deployments can spend more on validation than they save in execution. The savings at each generation and the total cost including validation in Appendix E quantify this distinction. Preserving current eligibility can therefore support useful improvement while protecting the actions carried out between edits. 

4 Related Work 

Recursive self-improvement. RSI studies how an agent’s acquired capabilities can feed into its own subsequent improvement (Schmidhuber, 2007, Duan et al., 2026). Surveys organize agent evolution across model, memory, tool, and architectural changes (Gao et al., 2025, Fang et al., 2025). STOP improves optimization procedures, DGM retains an evolving archive of agents, and Gödel Agent revises its own logic (Zelikman et al., 2024, Zhang et al., 2025a, Yin et al., 2025). Related work automates agent design, workflow search, and reusable skill acquisition (Hu et al., 2025, Zhang et al., 2025b, Wang et al., 2023, Zheng et al., 2025). These directions make persistent reuse central to capability growth. Our study examines the safety of that reuse across generations by separating historical evaluation, current execution eligibility, and the implementation used to generate subsequent changes. Matched comparisons establish when an improvement loop preserves a detected failure despite having a valid alternative. 

Agent safety. Agent-SafetyBench and ToolEmu evaluate harmful actions in tool environ-ments (Zhang et al., 2024, Ruan et al., 2024). AgentDojo evaluates prompt-injection attacks and defenses (Debenedetti et al., 2024). Other studies examine risks in reusable skills, agent memory, and the transition from a safe model to an acting system (Hao et al., 2026, Chen et al., 2024, Wei et al., 2026). Privilege controls and guard agents constrain what actions may execute (Shi et al., 2025, Xiang et al., 2025), while misevolution and lifecycle studies analyze how risks emerge or amplify during agent adaptation (Shao et al., 2026, Han et al., 2026, Lin et al., 2026). We extend this perspective to the decisions that keep behavior active across generations. Independent effect traces distinguish authorization from task success, and matched retention and editing-source comparisons explain why detecting a failure need not end unsafe action. 5 Discussion 

A program’s authorization must be assessed under its current contract. A historical pass remains a record of the conditions that were tested, but a new dependency can change which actions are permitted. Regression tests can expose that change without deciding what executes next. Our readout comparisons show the consequence directly: an archive may contain a correct repair while its stored ranking continues to favor an invalid program. A controller can record which contract each evaluation used and recheck deployment candidates when a relevant dependency changes. Execution and further improvement also require different decisions. A controller can protect the next action through a currently passing fallback while the editor continues searching for a better implementation. It can independently choose the implementation used to generate that next revision. The shared-root results show why this matters: identical failures and feedback can lead to different recovery trajectories depending on the editing source. Stronger editors shorten some repair processes, but protection is still needed while repair is underway. Revalidation identifies programs that still pass, fallback determines what runs after rejection, and the editing source determines where the next repair attempt starts. Safety evaluation should follow selected behavior throughout that loop. Final correctness describes the eventual outcome, while intermediate actions reveal whether reaching it involved unauthorized execution. The same distinction applies to utility: a cheaper program is useful only if it completes permitted work, and the cost of validating it must be included when assessing deployment benefits. Tests with new combinations of events still expose failures in programs that pass the current suite, so revalidation remains limited by test coverage. An evaluation should therefore record which programs run, whether their actions remain authorized, and which conditions were tested at each generation, alongside the final task score. 

6 Conclusion 

We study agent safety across generations of recursive self-improvement and distinguish detecting a failure, making a repair available, and ending unsafe execution. Optimizations can pass the full initial suite yet become unsafe under a new authorization dependency. Historical scores may preserve these failures despite correct alternatives in the archive, while keeping the incumbent after rejection provides another route to persistence under an unchanged contract. These findings place safety responsibilities in selection and retention as well as in validation. Recovery also depends on the implementation supplied to the next edit. Our controlled testbed separates these decisions through paired histories and independent effect traces. Current deployment validation, refreshed archive scores, and validated fallback improve safety while preserving useful efficiency gains in the studied tasks. Safety must be preserved throughout improvement, even when no revision is accepted. 

Limitations. We study controlled authorization tasks with fixed LLM editors, initially correct founders, and externally specified contracts. Our conclusions assume correct valida-tors within the tested conditions. Larger deployments, longer histories, and jointly evolving editors remain directions for further study. A Methods and Statistics 

A.1 Dataset Construction 

Instance and generation. A dataset instance is an ordered event stream, not a standalone prompt. Setup and update events change the environment, while requests ask the evolving program to perform protected actions. Seeded templates specify eight categories per family: basic behavior, repetition, denial, scope, updates, rebinding, boundaries, and ordering. Each category contains three probes. Generators instantiate identifiers, scopes, and category-specific state changes so the same contract can be tested across reproducible workloads. Consent shares the approval event templates but uses a distinct service contract for asking and reusing user agreement. 

Splits and matched reuse. Each block fixes a task family, editor, version-query cost, and seed, then generates 24 public, 24 audit, and 24 hidden streams with separate split seeds. Public tests govern eligibility and feedback, audit tests support rollback, and hidden outcomes are measured without entering either decision. Conditions and generations reuse the same streams within a block. The 288 blocks give 20,736 stream assignments indexed by block, split, and probe (Table 4). This count includes streams assigned to different blocks even when they share an event sequence. It does not count distinct authorization problems. Repeated program executions do not create additional dataset instances or independent statistical samples. 

Oracle and observable outcomes. The environment computes permission from its current state and records each protected effect independently of the program’s return value. Full correctness requires the expected outputs and effects, including completion of permitted requests. A program cannot erase an unauthorized effect by suppressing its output, nor obtain full correctness by refusing every action. Records connect each request to service calls, effects, costs, and program identity. Fig. 13 illustrates one saved consent stream before and after repair, with the corresponding source change given alongside it. These records make it possible to distinguish proposing a repair, deploying it, and preserving safe behavior during subsequent edits.

A.2 Contracts and Execution 

Session authorization. Requests identify a tenant, session, and resource. A payload may be returned only when permission is current and the session is not revoked. State changes grant or remove permission, revoke a session, or restore it. Reusing authorization for another scope or after revocation violates the contract. Checking costs ten units and a protected read costs one. 

Filesystem containment. Requests specify a path and content. The program must resolve the path and write only when its canonical target lies inside the authorized root. Symbolic-link targets can change between requests. Correctness requires the requested target and content as well as containment. Resolution costs eight units, containment testing three, and writing one. Evaluations use disposable filesystem fixtures with no access to arbitrary external files. 

Tool approval. A token authorizes a tool and resource, an amount within a limit, a finite number of uses, and an expiration time. State changes can mint, cancel, renew, or rebind authorization and advance logical time. Execution consumes one use and changes the global version. The program returns the execution result when permitted and otherwise produces no effect. Approval costs 12 units and execution one. 

Structured user consent. The request identifies a simulated user, tool, resource, and amount. Willingness is private to the simulator. Asking presents these details and returns agreement, scope, version, remaining uses, and expiration. Agreement permits reuse for the

Tests and workloads. Eight categories cover basic allowed behavior, repeated requests, denial, scope changes, state updates, authorization rebinding, boundary values, and operation ordering. Three instances per category give 24 streams. The routine gate uses basic, repetition, denial, and scope categories. Full validation uses every category in the current public suite. Within a block, workloads remain fixed across conditions and generations. Hidden outcomes never enter selection or feedback.

A.4 Statistical Inference 

Each main task-family contrast pairs 72 blocks by model, query cost, and seed. We resample blocks within each model, retain equal model weights, and use 10,000 bootstrap resamples for percentile 95% intervals. H Extended Related Work 

H.1 Recursive Self-Improvement 

The Gödel machine formulates self-improvement through provably useful code rewrites (Schmidhuber, 2007). Empirical systems use executable feedback where such proofs are unavailable. STOP improves an optimization procedure, DGM maintains an archive of coding agents, and Gödel Agent modifies its own logic through LLM-generated changes (Zelikman et al., 2024, Zhang et al., 2025a, Yin et al., 2025). AlphaEvolve searches for improved algorithms using program evaluation (Novikov et al., 2025). These systems motivate studying the agent components that carry improvement across iterations. Our experiments hold the editor and editing procedure fixed to isolate changes in the selected task program and its authorization behavior. The source audit in Table 8 distinguishes execution of upstream components from inspection of other systems and does not assume a universal retention rule. Harness engineering and disclosure studies identify the surrounding execution harness as a central variable in agent reliability and evaluation (Li et al., 2026, Zhang et al., 2026c). Agent optimization also changes workflow structure and prompts. ADAS searches for agent designs expressed in code, and AFlow searches over workflows (Hu et al., 2025, Zhang et al., 2025b). GPTSwarm optimizes computational graphs of agents (Zhuge et al., 2024). Promptbreeder evolves task prompts and their mutation prompts, DSPy compiles and optimizes declarative language-model pipelines, and TextGrad propagates textual feedback through compound systems (Fernando et al., 2024, Khattab et al., 2024, Yuksekgonul et al., 2024). EvoAgentX integrates workflow generation and optimization (Wang et al., 2025a). These systems optimize agent designs, workflows, and prompts for later use. Our experiments ask whether an earlier evaluation remains sufficient when the authorization conditions for that use change. 

H.2 Feedback, Memory, and Skills 

Reflexion stores linguistic feedback to improve later decisions, while Self-Refine iteratively revises an output using feedback from the same model (Shinn et al., 2023, Madaan et al., 2023). ExpeL extracts reusable insights from experience, and Memento adapts through memory-based learning without fine-tuning the underlying LLM (Zhao et al., 2024, Zhou et al., 2025). These approaches show that adaptation need not change model weights (Niu 

> 41 Zhang et al. · Safety Must Survive Self-Improvement

et al., 2026). Continual visual adaptation similarly retains reusable prompts across changing domains (Zhang et al., 2025c). These methods make the content supplied to future decisions consequential. Our shared-root experiment controls the starting failure and changes the code supplied to the next edit, providing a direct comparison of recovery under alternative editing contexts. Voyager accumulates executable skills, SkillWeaver discovers and practices reusable web APIs, and Alita constructs and reuses external capabilities (Wang et al., 2023, Zheng et al., 2025, Qiu et al., 2025). Reuse is central to their capability gains. The permission-cache examples in this paper examine a safety condition on reuse: the dependencies supporting a past decision must still hold when that decision is applied. Our tasks test this dependency through recorded permission checks and actions. Surveys organize self-evolving agents across model, memory, tool, and architectural changes (Gao et al., 2025, Fang et al., 2025), within which our setting focuses on executable agent components and their selection history. 

H.3 Safety During Adaptation 

Open-ended search raises tensions between continued innovation and control (Ecoffet et al., 2020), and safety analyses of open-ended systems emphasize evolving behavior and initial assumptions (Sheth et al., 2025). Misevolution supplies empirical evidence of risks across model, memory, tool, and workflow evolution, including unsafe tool creation and reuse (Shao et al., 2026). ATP studies drift through self-interested exploration and diffusion of strategies across agents (Han et al., 2026). Lifecycle analysis identifies how adversarial influences can persist and amplify through evolving systems (Lin et al., 2026). These are closely related findings. Our additional evidence comes from matched interventions: the same archive under different eligibility rules, the same rejected candidates under different fallbacks, and the same failed roots under different editing sources. Persistent agent state is also an attack surface. AgentPoison targets long-term memory and retrieved knowledge, while work on episodic memory discusses both safety risks and opportunities for monitoring (Chen et al., 2024, DeChant, 2025). In our controlled experiments, neither poisoned memory nor adversarial editing instructions are needed. Prompts require preserving authorization. Invalid reuse can instead arise through optimization or a newly revealed dependency, after which selection determines whether the failure remains active. 

H.4 Objectives and Parameter Adaptation 

Reward-hacking analyses formalize differences between a proxy objective and the intended outcome (Skalse et al., 2022, Pan et al., 2022). Reward-tampering work distinguishes interven-tions on a reward function from changes to its inputs (Everitt et al., 2021). Historical archive scores present a related but more specific mismatch: an evaluation measured under an earlier contract can rank an implementation above currently correct alternatives. Our fixed-pool and matched-readout experiments control candidate quality and availability, allowing persistence to be attributed to selection rather than inferred from performance alone. Parameter adaptation offers a complementary route to improvement. Absolute Zero and R-Zero develop self-generated training tasks, and RAGEN studies trajectory-level reinforcement 

> 42 Zhang et al. · Safety Must Survive Self-Improvement

learning for interactive agents (Zhao et al., 2025, Huang et al., 2025, Wang et al., 2025b). Broad model reports such as Qwen3 document capability and efficiency development at the model level (Yang et al., 2025). Safety can change under fine-tuning even without malicious user intent, and narrow insecure-code training can induce broader misalignment (Qi et al., 2024b, Betley et al., 2025). Sleeper Agents studies persistence of trained deceptive behavior, shallow-alignment analysis examines vulnerable response prefixes, and Safe LoRA seeks to preserve safety during efficient adaptation (Hubinger et al., 2024, Qi et al., 2024a, Hsu et al., 2024). Our fixed-model design isolates retention and editing context from these changes to learned parameters. 

H.5 Evaluation and Enforcement 

Functional code benchmarks such as HumanEval and SWE-bench assess generated programs and repository changes (Chen et al., 2021, Jimenez et al., 2024). RedCode evaluates risky execution and generation, whereas CWEval jointly tests functionality and security with outcome-based oracles (Guo et al., 2024, Peng et al., 2025). Our full-correctness metric similarly requires both legitimate completion and authorized effects. Following selected programs across generations then distinguishes never entering failure, retaining a failure, repairing it, and producing a new failure after recovery. ToolEmu evaluates risks through emulated tool execution, and Agent-SafetyBench covers diverse interactions (Ruan et al., 2024, Zhang et al., 2024). AgentDojo (Debenedetti et al., 2024) and InjecAgent (Zhan et al., 2024) evaluate indirect prompt injections. SafeArena studies harmful web-agent tasks, MobileSafetyBench studies device control, and AgentDAM evaluates unnecessary use of sensitive information (Tur et al., 2025, Lee et al., 2024, Zhar-magambetov et al., 2025). Complementary studies examine agentic multimodal red teaming (Zhang et al., 2026a) and safety in agent social platforms (Zhang et al., 2026b). These bench-marks cover risks and environments beyond our controlled contracts. Our native transfer study uses the released 𝜏 and 𝜏 2 workflows, which evaluate interactive task completion under domain policies (Yao et al., 2024, Barres et al., 2025). Its mixed outcomes support keeping task success and authorization behavior separate rather than treating one as a substitute for the other. Progent expresses programmable privilege controls, GuardAgent checks actions against safety requests through generated guardrail code, and TrustAgent uses an agent constitution to guide safer behavior (Shi et al., 2025, Xiang et al., 2025, Hua et al., 2024). Such controls can complement validation and restoration. Our execution-guard condition blocks unauthorized effects but does not repair evolved code that omits permitted work. Regression-testing research likewise studies behavioral preservation under program evolution and reduced test suites (Shi et al., 2018). The additional issue here is that retained code both executes and shapes the next model-generated revision, so recovery depends on editing source as well as detection coverage.

I Scope and Limitations 

Editors differ in failure incidence and repair. Qwen accounts for most of the recovery difference between editing sources in the shared-root study. In the runs that start from correct programs, founder editing ends with fewer unsafe consent programs for all original editors. The identical-candidate study also shows that keep retains rejected programs with both GPT and Sonnet. The framework experiments run OpenEvolve components, upstream DGM functions, and Casbin on authorization workloads we constructed. Native 𝜏 workflow transfer is mixed and does not establish a systematic increase in authorization failures (Appendix G). The main controls assume a correct founder, an externally specified contract, and a correct validator. We do not vary the validator’s implementation. The all-history-invalid control tests restoration without a valid founder, and independent compositions expose coverage gaps. Service costs measure weighted operations rather than model inference or latency. Our fixed-editor experiments isolate persistent agent components and selection decisions within RSI, leaving joint evolution of the editor and its improvement strategy to further study.
