Abstract 

Coding agents based on frozen language models can improve their performance by refining the external context they rely on, without updating model weights. In this paper, we study recursive self-improvement (RSI) through behavioral spec-ifications : natural-language code documentation that describes the behavior of program entities and guides agents in generating correct code. We formulate a self-improvement loop in which an agent generates code from its current speci-fications, evaluates the generated code using execution-verified tests, and refines the specifications based on observed failures. The improved specifications then guide subsequent code generation, allowing the agent to progressively improve its understanding of the codebase. However, recursive refinement is challeng-ing because program entities are interdependent. Improving the specification of one entity can inadvertently degrade the correctness of others, a phenomenon we call output coupling . This creates a whack-a-mole effect in which local improve-ments cause regressions elsewhere, preventing consistent progress. We introduce SPEC FORGE , a multi-frontier tree search framework that addresses this challenge through three mechanisms: (i) Pareto-guided state selection preserves comple-mentary specification states and prevents premature commitment; (ii) dependency-constrained entity selection prioritizes callee-before-caller refinement; and (iii) error-diversified expansion explores multiple refinements using different subsets of test failures. On D EV EVAL +, S PEC FORGE achieves the best performance across five backbone models, including a 94.9% solve rate with Claude-4.5-Sonnet and a 5.7-percentage-point average improvement over the strongest baseline. The improved specifications also make the agent better at tasks outside the loop: they transfer to cross-language translation and to new-feature implementation, where they outperform the benchmark-provided requirement documents. The code and data are available at https://github.com/ccsnow127/SpecForge .

1 Introduction 

Large language models are increasingly used as autonomous coding agents. Systems such as Cursor [1], Codex [2], and Claude Code [3] can generate code, implement new features, and modify existing software with limited human intervention. Their effectiveness, however, depends heavily on how well they understand the behavior of the codebase they work with. This understanding is essential for tasks such as repository-level code generation [4, 5], legacy system migration [6], cross-language reimplementation [7, 8], and new-feature implementation [9]. One way to provide such understanding is through behavioral specifications : natural-language code documentation that describes what individual program entities (e.g., functions, classes, and methods) do, including their inputs, outputs, and important behavioral constraints. Unlike traditional documentation intended

primarily for human readers, these specifications serve as actionable knowledge that coding agents can use to generate and modify code. Importantly, because specifications are expressed in natural language, agents can also revise them based on feedback, creating an opportunity for self-improvement without changing the underlying language model. This motivates specification-mediated recursive self-improvement (RSI) , in which a coding agent iteratively improves its own behavioral specifications using feedback from code generation and execution, without modifying the underlying model weights. Starting from initial specifications, the agent generates code conditioned on these specifications alone and evaluates the generated implementations through unit tests. Test failures reveal missing or ambiguous behavioral information, which the agent uses to refine the specifications. The refined specifications then guide the next round of code generation, forming a recursive self-improvement loop. In our setting, the tests are automatically generated from the reference implementation and validated through execution, retaining only tests that pass. This provides reliable, execution-grounded feedback without requiring human annotations. Importantly, the objective is not to improve the reconstructed code itself, but to produce more accurate behavioral specifications. Their quality is measured not by readability or similarity to human-written documentation [10, 11], but by whether an agent can reconstruct behaviorally correct code from them. The resulting specifications capture reusable knowledge of the existing codebase, which can support downstream tasks such as cross-language translation and new-feature implementation, even when no reference implementation of the desired output is available. Despite its promise, specification-based RSI faces a fundamental challenge: program entities are not independent . Existing language-space optimization methods, such as MIPROv2 [12], GEPA [13], and ACE [14], demonstrate that language models can improve their own context through iterative refinement and feedback [15, 16]. However, directly applying this approach to behavioral specifi-cations is difficult because changes to one entity can affect the behavior of others. We refer to this phenomenon as output coupling . It arises in two ways. First, dependency coupling occurs when the correctness of a caller depends on the behavior of its callees. Refining a caller before its callees are correctly specified can therefore produce misleading feedback. Second, generation coupling 

occurs because a coding model may condition on the entire specification bundle, so modifying one specification can change how other entities are generated, even without direct dependencies. Consequently, an update that fixes one entity may break another, creating a whack-a-mole effect: improvements are repeatedly undone by subsequent refinements, and the optimization process may oscillate rather than converge. For recursive self-improvement to be effective, it must therefore address three requirements: preserving previous progress, respecting dependencies between entities, and handling noisy or incomplete feedback during refinement. To address these challenges, we propose S PEC FORGE , a multi-frontier tree search framework for recursive self-improvement through behavioral specifications. Instead of following a single sequence of specification revisions, S PEC FORGE explores multiple candidate specification states through three complementary mechanisms: ❶ Where to search: Pareto-guided state selection maintains an archive of non-dominated specification states with complementary strengths across program entities. This preserves alternative refinement paths and prevents premature commitment to a single solution. ❷ What to refine: Dependency-constrained entity selection uses the program’s call graph to restrict refinement to entities whose callees have already been resolved. A discounted-UCB bandit then adaptively allocates the refinement budget among eligible entities. ❸ How to refine: Error-diversified expansion generates multiple refinement candidates from different subsets of failing tests, allowing the search to explore alternative explanations for observed failures and reducing sensitivity to noisy feedback. Together, these mechanisms mitigate refinement interference and enable improvements to accumulate across recursive iterations. We evaluate S PEC FORGE on D EV EVAL +, where behavioral specification quality is measured by the correctness of code reconstructed from the generated specifications. Across five backbone language models, S PEC FORGE consistently outperforms strong documentation, prompt-optimization, and coding-agent baselines. In particular, it achieves a 94.9% solve rate with Claude-4.5-Sonnet and improves over the strongest baseline by 5.7 percentage points on average. We further evaluate whether the optimized specifications remain useful beyond the original code-generation task. Results on cross-language translation and new-feature implementation show that these specifications provide reusable behavioral knowledge that improves coding-agent performance in different software engineering settings. These findings suggest that refining behavioral specifications provides a practical approach to recursive self-improvement for coding agents, without requiring model weight updates. 2Our main contributions are summarized as follows: • We study specification-mediated recursive self-improvement for coding agents, in which behavioral specifications are iteratively improved through code generation and execution feedback. We identify 

output coupling as a central challenge that prevents naive iterative refinement from accumulating progress. • We introduce S PEC FORGE , a dependency-guided multi-frontier tree search framework that com-bines Pareto-guided state selection, dependency-constrained entity selection, and error-diversified expansion to mitigate refinement interference and enable cumulative specification improvement. • We demonstrate that S PEC FORGE consistently outperforms strong baselines on D EV EVAL + across five backbone models, and that its optimized specifications improve downstream cross-language translation and new-feature implementation. 

2 Problem Formulation 

We study behavioral specification optimization : given source code, the goal is to produce, for every program entity, a natural-language specification from which a code-generation model can reconstruct a correct implementation without seeing the code. Unlike documentation, whose objective is human readability, a specification is judged by downstream behavioral utility —whether it contains enough precise semantic information for an LLM to synthesize correct code. Consider a code module with n program entities E = {e1, . . . , e n}, such as functions, classes, or methods. Let G = ( E, E ) be the call graph, where (ei, e j ) ∈ E indicates that entity ei invokes entity 

ej . For evaluation, we assume a set of unit tests T , and each test t ∈ T is attributed to a target entity through a mapping α : T → E . We denote by Ti = {t ∈ T : α(t) = ei} the tests associated with entity ei. Let D = ( d1, . . . , d n) denote a specification bundle, where di is the specification for entity 

ei. Given a code generation model G, the generated implementation for entity ei is ci = G(D, e i),and the full generated module is C(D) = ( c1, . . . , c n).

Output Coupling. The central challenge is that program entities cannot be optimized independently. First, dependency coupling arises because if ei calls ej , then the correctness of ci depends on the realized behavior of cj . Second, generation coupling arises because the code generator conditions on the full specification bundle D, so changing dj may alter the generated code for ei even without a direct call edge. Together, these effects produce a whack-a-mole phenomenon: refining the specification of one entity may improve that entity while destabilizing others. Search Formulation. The optimization is difficult because specification quality is only observable 

after code generation and execution. This makes behavioral specification optimization a structured search problem over specification states. Different partial solutions resolve different subsets of entities, and these resolved subsets determine which subsequent refinements are meaningful under dependency constraints. 

3 Proposed Method 

We propose S PEC FORGE , a multi-frontier tree search framework for behavioral specification op-timization. S PEC FORGE instantiates the self-improvement loop of §1 as search: each node is a specification state evaluated by executing the code generated from it, each edge is one self-revision driven by the failures of that code, and every revision starts from a state that earlier revisions produced. 3Figure 1: Search tree view of behavioral specification optimization. Each node is a specification state. Different states solve different subsets of entities and therefore expose different eligible next refinements. Rather than committing to a single rewrite trajectory, our solution preserves multiple competitive frontiers and expands them selectively. Figure 1 illustrates the search process: specification optimization proceeds not as a single rewrite tra-jectory, but as search over multiple partial solutions with different future refinement opportunities. By managing this search so that local refinements accumulate into stable global progress, S PEC FORGE 

directly targets the whack-a-mole behavior induced by output coupling.

This single-entity transition is the basic search step in S PEC FORGE : it keeps refinements localized, makes feedback easier to attribute, and allows the method to explore multiple competing partial solutions in parallel. 

Multi-Frontier Tree Search. Starting from a root node v0 corresponding to the initial specifications, SPEC FORGE maintains a Pareto archive A of non-dominated states (initialized as {v0}) together with a shared entity-selection bandit. Each iteration resolves three coupled decisions: where to search (§3.1), what to refine (§3.2), and how to refine (§3.3). Concretely, the iteration (i) samples a parent node v from A; (ii) selects an eligible entity e to refine via a discounted-UCB policy over per-entity gap-closing rates; and (iii) expands v into W children, each obtained by substituting a refined specification d′

The W children are then folded back into both upper levels: non-dominated children enter A, introducing new frontier diversity for future state selection, and the best child’s ∆ϕe updates the bandit for future entity selection. Once B iterations, SPEC FORGE returns the specification bundle Dv achieving the largest |S| over all visited states. Figure 2 and Algorithm 1 summarize the procedure.

Frequency-Weighted Sampling. To select which archive node to expand, we sample from the Pareto front of A (Algorithm 2). For each entity ei, we identify the archive node(s) attaining the highest ϕi and assign credit to those node(s), splitting it evenly in the case of ties. A node’s sampling weight is the total credit it accumulates across entities. This biases expansion toward nodes that are frontier-best on more entity-wise dimensions, thereby preserving complementary search frontiers rather than collapsing prematurely to a single trajectory.

3.3 Error-Diversified Expansion 

Given a selected state v and entity e, the third step expands v into W child states, each representing a distinct refinement of de. The key challenge is that failing tests are diagnostically heterogeneous: 5some directly expose the behavioral detail missing from the specification, while others are redundant, weakly informative, or induced by cascading dependency errors. This is consistent with prior findings that test cases differ substantially in fault-localization value, LLM-generated tests often cluster around similar patterns, and adding more tests can even hurt diagnosis when uninformative cases dilute the signal [18, 19, 20]. More broadly, LLMs are known to be sensitive to irrelevant or noisy context in both in-context learning and RAG settings [21, 22, 23]. 4 Experiments 

Our experiments test the claims behind specification-mediated self-improvement: that improvements accumulate instead of oscillating (§4.2 and §4.3), that each component of S PEC FORGE contributes to the stability of the loop (§4.4), and that the improved specifications make the agent better at tasks outside the loop (§4.5). 

4.1 Setup Benchmark. We evaluate S PEC FORGE on D EV EVAL +, a benchmark for evaluating behavioral specifications through code reconstruction and execution-based verification across modules with complex inter-entity dependencies. It consists of 20 Python modules , 247 entities , and 760 test cases .The modules are drawn from DevEval [5] and supplemented with additional GitHub repositories to broaden domain coverage, including finance, biological analysis, and signal processing. D EV EVAL +is structurally nontrivial, with an average dependency depth of 4.2, making it a suitable testbed for studying output coupling under repository-scale generation (full details in Appendix H). 

Baselines. We compare S PEC FORGE against five groups of baselines: • Static documentation methods : RepoAgent [10] and DocAgent [11], which generate human-oriented documentation without execution feedback; we evaluate their documentation in the specification role. • Prompt optimization methods : MIPROv2 [12], GEPA [13], and ACE [14], which optimize the instruction context used to generate specifications, rewriting the full specification bundle monolithi-cally at each iteration based on code-generation feedback. • Commercial coding agents : Cursor [1] and Claude Code [3], evaluated in four variants: (1) base ,using default settings; (2) +Topo , which supplies reverse topological order as additional context; (3) +Test , which prompts the agent to generate tests and iteratively refine code; and (4) +Topo+Test ,which combines both augmentations. 2

Table 1 presents comprehensive comparisons across methods and base LLMs (50 rollouts). S PEC -FORGE achieves the highest solve rates across all models: 88.9% with Qwen3-235B-A22B, 89.6% with Gemini-2.5-Flash, 90.9% with GPT-4o, 91.0% with Gemini-3.1-Pro, and 94.9% with Claude-4.5-Sonnet. The results reveal a clear hierarchy of failure modes. Static methods (14.5–35.3%) expose a 

documentation–specification gap : documentation optimized for human readability appears imprecise about behavior to serve as a specification for code-synthesis models, which interpret underspecified phrases literally but resolve ambiguities unpredictably. Monolithic prompt optimizers improve substantially—ACE reaches 62.8% on GPT-4o via its generate-reflect-curate pipeline—but suffer from attribution failure (cannot identify which entity caused a test failure) and coupling amplification 

(a single rewrite alters all entities simultaneously). Iterative refinement with topological ordering reaches 54.3% on GPT-4o but plateaus due to the whack-a-mole phenomenon: without Pareto archiving and diversified exploration, correct ordering alone cannot overcome interference at the same topological level. DOC SEARCH is the strongest baseline (81.5–90.4%) and the only one that optimizes the same objective. 5 Related Work 

Recursive Self-Improvement. Self-improving LLM systems differ first in the substrate into which an improvement is written. Weight-space methods write into model parameters: the model is fine-tuned on data it generated itself [25, 26], on rewards derived from its own outputs [27], or on rewards from a grounded environment [28]. The gain is amortized across tasks, but it cannot be read, diffed, or reverted. Context-space methods keep the weights frozen and write into the harness instead, through verbal self-refinement [29, 30, 16], prompt search and textual gradients [15, 31, 32, 33, 12, 13], experience memory [14], skill and tool synthesis [34], or search over the whole scaffold [35]; at the frontier, the procedure that performs the update is itself rewritten [36, 37, 38]. The improvement signal ranges from the model’s own judgment [39, 40] to external verifiers such as tests [41, 42, 43], compilers [44, 45], and environments [34, 46]. S PEC FORGE is a context-space method with an execution-based improvement signal and a fixed update procedure. The key difficulty in such a recursive self-improvement loop is that behavioral specifications are inherently coupled through the code generated from them, so that an improvement to one can cause a global regression and make the iterative process oscillate. 

Coding Agents. Coding is among the most rapidly advancing capabilities of LLM agents, in large part because code is executable, verifiable, and searchable: a candidate can be run, checked against tests, and improved by search. Agents such as Cursor, Codex, and Claude Code [1, 2, 3] now resolve issues and implement features across entire repositories [47, 48, 4, 5, 9]. The same property is carrying agents beyond conventional software, wherever the artifact can be expressed as a program or other interpretable text: games [49], explanatory videos rendered from animation code [50, 51], 3D scenes written as Blender scripts [52], and symbolic music [53]. S PEC FORGE is complementary to these agents: it supplies behavioral specifications that a coding agent can condition on, which in our experiments improve cross-language translation and new-feature implementation (§4.5). 

Code Documentation. Documentation generation has evolved from template-based heuris-tics [54, 55, 56] through neural summarization [57, 58] to modern LLM-based repository-level approaches. RepoAgent [10] extracts structural patterns from repositories to generate API references with hierarchical organization, while DocAgent [11] employs retrieval-augmented generation to produce context-aware explanations grounded in relevant code snippets. Both optimize for subjective quality metrics—clarity, completeness, and helpfulness—evaluated through human assessment or proxy metrics like BLEU scores against reference documentation. These approaches uniformly assume documentation serves human developers and measure quality through readability heuristics rather than downstream task performance. See Appendix K for further related work. 

6 Conclusion 

We presented S PEC FORGE , a multi-frontier tree search framework that makes specification-mediated self-improvement stable and compounding. A frozen coding agent improves by rewriting the behavioral specifications in its harness from the failures of the code it writes from them; unlike documentation written for human readers, a specification is judged only through the code it induces. Within this formulation, the central challenge is output coupling : because generated entities are behaviorally interdependent, locally beneficial refinements can trigger global regressions, rendering standard monolithic or sequential refinement unstable. S PEC FORGE addresses this challenge through Pareto-guided frontier preservation, dependency-constrained entity selection, and error-diversified expansion, enabling stable progress under coupled search dynamics. Empirically, it consistently outperforms strong baselines on D EV EVAL +, exhibits superior search efficiency and robustness, and produces specifications that improve downstream performance in both cross-language translation and new-feature implementation, indicating that what the loop improves is reusable knowledge of the codebase rather than a fit to the tests that guided it. 10 References

B.1 Why Multi-Frontier Search Escapes Certain Frontier-Local Optima 

A central role of the Pareto archive in S PEC FORGE is to prevent the search from collapsing onto a single refinement trajectory too early. We formalize this benefit through the notion of frontier-local optimality : a state may be locally saturated with respect to its currently eligible refinements, while another non-dominated state still exposes a different eligibility frontier from which progress remains possible. 

Definition 4 (Frontier-Local Optimum) . Let v = ( Dv , ϕv , Sv ) be a search state with eligibility frontier Eelig (v). We say that v is a frontier-local optimum if for every eligible entity e ∈ E elig (v) and every admissible single-entity refinement v e

−→ v′,

|S v′ | ≤ |S v |. (8) 

That is, no refinement available from the current frontier increases the solved-set objective. 

This notion captures the practical failure mode of single-path refinement: once the current state becomes frontier-locally optimal, all subsequent search effort is confined to a neighborhood with no objective improvement. The key observation is that frontier-local optimality is state-dependent :because eligibility depends on the solved set Sv , two states with similar objective values may expose different feasible next refinements. 

Definition 5 (Archive Dominance) . For two states u and v, we say that u dominates v if 

ϕu ⪰ ϕv ⇐⇒ ϕi(Du) ≥ ϕi(Dv ) for all i ∈ [n]. (9) 

A Pareto archive A contains only non-dominated states. 

The importance of this criterion is that it preserves states with complementary strengths across entities rather than only the current best state under a scalar score. Such states can induce different solved sets and therefore different eligibility frontiers. 

Assumption 1 (Complementary Frontier Reachability) . Suppose there exist two non-dominated states u and v in the search tree such that: 1. u is a frontier-local optimum; 2. there exists an entity e⋆ ∈ E elig (v) \ E elig (u) and a refinement v e⋆

−→ v⋆ such that |S v⋆ | > |S v |.

17 This assumption states that one archived frontier may be saturated while another still contains a productive move. It is natural in our setting because eligibility is induced by the solved subset, and different trajectories typically solve different subsets of entities. 

Proposition 1 (Multi-Frontier Advantage) . Under Assumption 1, any search strategy restricted to expanding only the single incumbent state u cannot improve the objective |S| , whereas a multi-frontier strategy that retains both u and v in a Pareto archive has nonzero probability of reaching a state with strictly larger solved set. Proof. Since u is frontier-locally optimal, by Definition 4, every admissible refinement from u

satisfies |S u′ | ≤ |S u|. Hence any single-path strategy confined to descendants of u cannot obtain an immediate objective improvement. By Assumption 1, there exists another archived state v and an eligible entity e⋆ ∈ E elig (v) such that refining e⋆ yields a child v⋆ with |S v⋆ | > |S v |. Because u and v are non-dominated, a Pareto archive retains both states. Therefore, any archive-sampling policy that assigns nonzero probability to every archived state has nonzero probability of selecting v and then refining e⋆, reaching an improved state. Thus, retaining multiple non-dominated frontiers strictly enlarges the set of reachable improving moves compared with single-path search. Proposition 1 formalizes the role of the Pareto archive in escaping local optima. Its benefit is not merely diversity for its own sake; rather, archive diversity induces frontier diversity . Because eligibility is determined by the solved subset, preserving multiple non-dominated states preserves multiple feasible continuation sets. When one frontier is exhausted, another may still expose an improving refinement. The argument also clarifies why scalar best-first retention is brittle in our setting. A state with the highest current |S| or ¯ϕ need not be the most promising continuation state if its eligibility frontier is already saturated. By preserving non-dominated states with complementary per-entity strengths, the Pareto archive acts as a structural hedge against premature convergence. 

Implication for S PEC FORGE . In S PEC FORGE , multi-frontier search is realized by maintaining a Pareto archive over per-entity pass-rate vectors and sampling from it during expansion. This design ensures that the search does not over-commit to a single locally attractive trajectory, but can continue from alternative archived frontiers whose dependency structure admits further progress.

Empirical Motivation. Our theoretical treatment is motivated by two recurring empirical observa-tions from the software engineering literature. 1. Failing tests differ substantially in diagnostic value. Not all failures are equally informative for identifying the underlying defect. Some tests reveal the root cause directly, whereas others fail only through cascading effects or repeatedly exercise the same execution path. In the context of LLM-generated tests, Yuan et al. [18] observe that generated inputs often cluster around similar patterns, leaving critical edge cases underexplored and further increasing heterogeneity in diagnostic usefulness. 2. Using more tests can degrade diagnosis rather than improve it. Prior work on fault localization shows that adding tests beyond a certain point may reduce localization quality when additional tests contribute little new information. Chen et al. [19] show that excessive or low-value tests can dilute diagnostic signals, while Su et al. [20] demonstrate that carefully selected subsets can outperform the full test suite for fault localization. In our setting, these observations imply that the full failure set may contain substantial noise. We attribute noisy errors F− to three common sources: (i) cascading failures , where a test fails because a callee is incorrectly implemented rather than because the target entity’s specification is inadequate; (ii) redundant signals , where multiple tests expose essentially the same failure mode and therefore add little incremental information; and (iii) misleading co-occurrence , where presenting several errors together encourages the optimizer LLM to infer spurious patterns that are not causally related to the true knowledge gap. 

Remark 1 (Connection to Fault Localization) . Our result formalizes a central intuition from fault localization: for diagnosis, test quality often matters more than test quantity [20]. Diversified error-batch sampling can be viewed as a hedging strategy: by exploring multiple subsets of the failure set, it increases the chance of encountering a batch dominated by informative signals, without requiring prior knowledge of the latent partition between informative and noisy errors.

C.1 Recursive and Cyclic Call Graphs 

The eligibility frontier (Eq. (3)) requires every callee of an entity to be resolved before the entity can be refined. On a call graph with cycles this condition can never hold for the entities on a cycle, so SPEC FORGE removes cycles before search. 

Self-recursion. A self-call (e, e ) ∈ E is ignored when evaluating eligibility: an entity cannot wait for itself to be resolved, and its recursive behavior is described within its own specification de.22 Mutual recursion. We compute the strongly connected components (SCCs) of G and contract each SCC with more than one member into a single meta-entity . The search then operates on refinement units , each of which is either a single entity or a meta-entity. The condensation of G over these units is a DAG by construction, so the callee-before-caller order and the eligibility gate apply unchanged: a unit is eligible once it is unsolved and all units it calls are resolved, and a meta-entity counts as resolved once all of its members are solved. 

Joint refinement of a meta-entity. When a meta-entity is selected, its members are refined together in a single expansion. The refinement prompt presents the source code and current specifications of all members, states that they are mutually recursive, and requires a complete replacement specification for every member, so that the specifications of the cycle remain consistent with one another. The resulting specifications are substituted into Dv together, and the child is evaluated as for any other expansion. 

C.2 D-UCB Bandit Details 

The entity selection bandit maintains a single set of statistics shared across all state nodes. We use Discounted UCB [17] with the following configuration: 

Reward Normalization. After each expansion of entity e with observed improvement ∆ϕe, the normalized reward is computed as: 

ˆre = ∆ϕe

1 − ϕe

, (32) where ϕe is the pass rate before refinement. This isolates the gap-closing rate θe from the remaining gap (1 −ϕe), preventing entities with large gaps from receiving inflated rewards. 

Discounted Statistics. At each update step, all arms’ statistics are discounted before incorporating the new observation: 

nγ (e) ← γ · nγ (e), ¯rγ (e) ← γ · ¯rγ (e), Nγ ← γ · Nγ ∀ e, (33) followed by nγ (e) ← nγ (e) + 1 , ¯rγ (e) ← ¯rγ (e) + ˆ re, and Nγ ← Nγ + 1 for the pulled arm. The discounted mean is ˆθe = ¯ rγ (e)/n γ (e).

Hyperparameters. 

• Discount factor γ = 0 .95 : yields an effective observation window of ∼1/(1 −γ) = 20 steps, allowing the bandit to adapt as callees stabilize and entity difficulty shifts. • Exploration constant C = 2 √2: following the standard UCB1 setting [59]. • Initialization : all arms start with nγ (e) = 0 , ¯rγ (e) = 0 . Untried entities receive score ∞× (1 −ϕe),ensuring they are explored first with gap-proportional priority. 

C.3 Expansion Implementation Details Error Batch Construction. We use beam width W = 3 throughout all experiments, balancing the hedging benefit of diversified expansion (Theorem 2) against per-iteration cost. Given failing tests Fe(v) for entity e at state v, we sample W batches independently: each batch ek is drawn by selecting ⌈|F e(v)|/2⌉ failures uniformly at random without replacement from Fe(v), with batches generated sequentially and any duplicate redrawn until W distinct batches are obtained. This ensures each batch covers roughly half the failure set while varying in composition across the W branches. 

Small Failure Set Handling. When |F e(v)| is too small for W distinct same-sized subsets to exist, we relax the batch-size constraint and draw W distinct nonempty subsets of Fe(v) covering a range of sizes—e.g., |F e(v)| = 2 admits the three subsets {f1}, {f2}, {f1, f 2}. Theorem 2 applies in all such cases since it requires only ej ⊆ F e(v).23 Diagnosis-Prescription Process. Each refinement follows a two-stage process. In the diagnosis 

stage, the LLM analyzes the error batch to identify the knowledge gap: what information is missing or ambiguous in the current specification that caused the incorrect generation. In the prescription stage, the LLM produces a targeted specification update addressing the diagnosed gap. This decomposition prevents the LLM from making unfocused edits and ensures each refinement is traceable to a specific failure signal. Prompt templates for both stages are provided in Appendix F.

D.4 Key Takeaways 

This module-level trace exposes three failure modes and their structural causes: 1. Dependency blindness (Iterative). The LLM’s reflection is a powerful diagnostic tool—it correctly identifies cross-entity dependencies as the root cause of failure. But without a mechanism to act on dependency structure, this diagnostic power is wasted. The cycling pattern (same entity targeted 3 times, same diagnosis, same ϕe=0% ) is a direct consequence of treating entities as independent. 2. Collateral damage (ACE). Global rewriting treats the specification bundle as a monolithic artifact, making it impossible to improve one entity without risking others. The regression at B=30 and subsequent two-step recovery illustrate the “two steps forward, one step back” dynamic that caps ACE’s effective progress rate. Even at convergence ( B=50 , ϕ=0 .717 ), entity-specific algorithmic details remain beyond the reach of global rules. 3. Structural unlocking (S PEC FORGE ). By constraining refinement to entities whose callees are already solved, SPEC FORGE converts callee improvements into free caller improve-ments. The B=40 cascade—where solving PnF.get ohlc data simultaneously unlocks 

PnF.get bar ohlc data —demonstrates that dependency-aware search does not merely avoid interference but actively exploits coupling as a source of compounding returns. 

E Fidelity of the Self-Generated Improvement Signal 

A recursive self-improvement loop is only as sound as the signal that drives it. In S PEC FORGE the loop is fully self-supervised: the agent synthesizes the tests that score its own specifications, and no external label enters the loop. This raises a question that the main results cannot settle on their own, because every method in Table 1 is evaluated on hidden ground-truth tests but optimized against self-generated ones: does the self-generated signal track true behavioral correctness, or does the search merely learn to satisfy its own tests? In the latter case the measured gains would constitute reward hacking rather than self-improvement. Two properties are therefore required of the signal. 

Fidelity : optimizing against the self-generated signal must yield essentially the same outcome as optimizing against the ground truth. Grounding : the signal must be derived from execution rather than from the model’s own judgment, since Theorem 1 shows that a corrupted signal degrades refinement quality monotonically. This section verifies both properties and characterizes how performance degrades as the signal is weakened. 

Construction of the signal. Test oracles are obtained by executing LLM-proposed inputs on the reference implementation to derive the expected outputs (§J); output correctness is therefore guaranteed by construction. The only residual imperfection lies in input quality: some generated inputs may be redundant, exercise overlapping code paths, or fail to cover critical edge cases. Error-diversified expansion (§3.3) is designed for precisely this kind of imperfection: by conditioning each child on a different subset of failing tests rather than on the full test set, it bounds the influence of any individual weak or redundant test. 26 Table 2: Sensitivity to feedback signal (GPT-4o, DevEval+).

Experimental design. We hold the search procedure, budget, and backbone (GPT-4o) fixed and vary only the improvement signal (Table 2). (i) Signal source : the LLM-generated tests are replaced by the hidden ground-truth tests, an oracle that is unavailable in practice and serves as an upper bound on signal quality. (ii) Signal grounding : execution feedback is replaced by an LLM-as-a-judge score of the generated code against the specification, i.e., the model evaluates itself without executing anything. (iii) Signal coverage : the coverage threshold τcov used during test generation is lowered from its default of 0.9 (§J) to 0.7, 0.5, and 0.3, so that the search is driven by progressively fewer tests. 

Fidelity: self-generated vs. ground-truth tests. Replacing LLM-generated tests with ground-truth tests improves ¯ϕ only marginally, from 93.2 to 94.8, corresponding to a gain of just 1.6 percentage points. The self-generated signal is thus near-equivalent to the ground truth as an optimization target: the loop does not exploit its own tests, and the improvements reported in Table 1 reflect genuinely better behavioral specifications rather than reward hacking. 

Grounding: execution feedback vs. LLM judgment. Replacing execution-based feedback with LLM-as-a-judge scoring causes a large performance drop from 93.2 to 73.6, i.e., a decrease of 19.6 percentage points. Self-assessment is exactly the corrupted-signal regime of Theorem 1: the robustness of the loop to imperfect tests stems from grounding in execution, not from tolerance to arbitrary noise, and the execution signal cannot be substituted by model judgment. 

Coverage: sparser generated test suites. Lowering the coverage threshold τcov from its default of 0.9 to 0.7 or 0.5 has only a very small effect on performance, with ¯ϕ remaining above 92. At the more aggressive setting τcov = 0 .3, performance decreases to 87.5, corresponding to an overall drop of 5.7 percentage points relative to the default configuration. Degradation is graceful rather than brittle: the loop does not depend on a complete test suite, only on an execution-grounded one. 

Implication for recursive self-improvement. Execution grounding matters more than signal density. Thinning the execution signal degrades performance gracefully: even the sparsest test suite (τcov =0 .3, 87.5) still outperforms the LLM judge (73.6) by 13.9 points. A sparse but execution-grounded signal is therefore a better optimization target than a dense judgment-based one. This points to a general principle: in recursive self-improvement, the agent may propose its own feedback signal, provided that signal is grounded in execution. It also explains why code is a privileged substrate for self-improvement. Code is executable, testable, and iterable by nature, so every attempt yields grounded feedback, such as failing assertions, type errors, and stack traces, which the agent can use as an improvement signal without any external supervision.

I New Feature Implementation Setup (SWE-D EV )

This section details the new feature implementation experiment of §4.5.2: how SWE-D EV tasks and their PRDs are constructed, what each condition receives, and what the comparison tests. 

Task construction. Each SWE-D EV instance is built from an open-source PyPI package with an executable, developer-written test file [9]. The test file is run under a tracer to obtain the call tree of the source functions it triggers; target functions are selected from this tree, and their implementations are removed from the repository. Difficulty follows call-tree depth: easy instances have depth 1–2, and hard instances have depth ≥ 3 and typically require implementing five or more interdependent functions. The test file is the evaluation oracle. 

How the PRD is generated. The PRD shipped with each instance is written by GPT-4o in two parts [9]. A module-level description is synthesized from the test file. A function-level description of each target is obtained by augmenting the target’s original docstring with implementation-level details, with the prompt conditioned on the full code of its file, including the target function itself. The PRD concatenates the module description with, for each target, its signature, the augmented docstring, and a list of related functions ( DEPENDENCIES ). The PRD is therefore derived from the tests and the reference implementation, and it describes only the functions to be implemented: existing functions that the targets call appear in the dependency list by name only, without any description of their behavior. 

Conditions. All conditions receive the same stubbed package source, in which the target functions are removed, and are scored by Pass@1 on the instance’s test file following the SWE-D EV protocol. They differ only in the accompanying text: • PRD+Source : the full SWE-D EV PRD described above. • Spec+Source (RepoAgent, Claude Code ∗, ACE, S PEC FORGE ): the signature and original doc-string of each target function, which state what the new feature must provide, together with the specifications of the existing codebase produced by the method. 

Specification generation and masking. Each method generates specifications on the complete package, so that the codebase is executable, as it is in real development before a feature is added, and every entity has a reference behavior from which S PEC FORGE can derive test oracles. Deleting the target functions from a complete module beforehand would leave the module unable to run, since the remaining code still references them, which would rule out execution-based optimization methods such as S PEC FORGE . Before the implementation step, we remove the specifications of the target functions. No method observes the instance’s evaluation test file. 

Additional results analysis. The two conditions trade task-specific information against codebase-level information. The PRD describes the target functions in detail but says nothing about the behavior of the existing code they build on; the Spec+Source conditions describe the target functions only 35 minimally but describe the whole existing module. New features are rarely self-contained: SWE-D EV 

targets call into existing functions, constants, and exception types, and a correct implementation must use them exactly as they behave. For example, in the vulture configuration task, the PRD requires 

check input config to validate values against DEFAULTS and to raise InputError , but never states which keys DEFAULTS contains or how InputError is constructed. We refer to this missing knowledge as the semantic gap of the PRD. The experiment therefore asks whether a better semantic understanding of the existing module lets an agent implement a high-quality feature from only the minimal information that defines it. Because the PRD condition receives strictly more target-specific information, derived from the reference implementation, the comparison is conservative for the Spec+Source conditions. 

J Test Case Generation 

This appendix describes the LLM-based test case generation process used to guide S PEC FORGE ’s search without access to ground-truth tests. 

J.1 Overview 

SPEC FORGE operates as a self-improving framework where the search is guided by LLM-generated 

test cases rather than ground-truth tests. This design choice reflects realistic deployment scenarios where comprehensive test suites may not exist. The key insight is that even imperfect tests provide valuable diagnostic signals—test failures reveal knowledge gaps in the specifications, enabling targeted refinement. The test generation process follows a generate-then-validate approach: 1. Test generation : The LLM generates complete test functions—including inputs, assertions, and error messages—based on entity signatures and reference source code. 2. Validation : Each generated test is executed on the reference implementation. Only tests that pass are retained; those that fail (due to incorrect assertions or invalid inputs) are discarded. Two additional filters are applied post-validation: (i) tests that reach the target entity only via transitive calls to other functions are discarded, ensuring each retained test directly exercises its target; and (ii) tests with identical normalized inputs and assertions are deduplicated. This ensures test correctness by construction: every retained test is consistent with the reference implementation and contributes a distinct diagnostic signal. 

J.2 Coverage-Driven Test Generation 

For each entity ei, we employ a coverage-driven generation strategy. The LLM generates test functions iteratively until branch coverage exceeds a target threshold τcov . Each iteration prompts the LLM to generate tests covering: • Normal cases : Typical usage scenarios with common input values • Edge cases : Boundary conditions (empty inputs, single elements, maximum values) • Corner cases : Special values that exercise specific code paths • Uncovered branches : When coverage feedback is available, tests targeting uncovered code regions The generation loop terminates when (1) branch coverage reaches τcov (primary criterion), or (2) the per-iteration branch coverage gain stays below a positive threshold ε for P consecutive iterations (no-progress early-stop). The loop is bounded because (i) progress iterations (gain ≥ ε) number at most ⌊1/ε ⌋, since branch coverage is bounded above by 1.0 and each contributes at least ε; and (ii) no-progress iterations (gain < ε ) cannot accumulate indefinitely because the P -th consecutive one triggers the early-stop. The generation prompt (provided in Appendix F) includes: • Entity signature and type information • Reference source code for understanding expected behavior 36 • Dependency signatures to ensure consistency with callees • Coverage feedback as (line number , source snippet ) pairs extracted from coverage.py ’s branch-coverage output, indicating which lines remain uncovered 

J.3 Quality Considerations 

While the validation step ensures test correctness, LLM-generated tests may have quality limitations that motivate our diversified error batch sampling (§3.3). 

Error Message Quality Variation. Since the LLM writes complete test functions, the diagnostic value of error messages depends entirely on how each assertion is written. Some tests include infor-mative messages (e.g., assert result == [1,2,3], f"Expected [1,2,3] got {result }")that directly reveal the failure mode, while others use bare assertions (e.g., assert result == expected ) that produce only AssertionError with no actionable signal. This heterogeneity is inherent to LLM-generated tests and cannot be controlled a priori. 

Input Quality Variation. Not all generated test inputs are equally informative. Some inputs may exercise redundant code paths, miss critical edge cases, or cluster around similar patterns. By conditioning refinements on different test subsets, diversified error batch sampling increases the probability of encountering informative failure signals. 

External Dependencies. External dependencies (filesystem, network, time, randomness) are de-tected via static analysis of import statements and AST patterns; the LLM is then prompted to isolate them through pytest fixtures (mocks for filesystem and network calls, frozen-time wrappers for time-dependent code) so that test outcomes remain deterministic and reproducible across runs. 

J.4 Hyperparameters 

We use the following hyperparameters for test generation: • LLM : GPT-4o (fixed across all experiments for consistency) • Temperature : τ = 0 .7 for input diversity • Coverage threshold : τcov = 90% branch coverage • No-progress patience : P = 2 consecutive iterations within ε = 0 .01 coverage gain 

K Additional Related Work 

Behavioral specifications as vertical knowledge. Behavioral specifications can be viewed as a form of vertical knowledge: repository-specific facts about what each program entity does, which are absent from a model’s weights and must be supplied to it at inference time. A broad line of work studies how such domain knowledge is acquired, structured, and used by LLMs. In cyber threat intelligence (CTI), LLMs have been used to construct knowledge graphs from unstructured threat reports [60], retrieval-augmented LLMs have been benchmarked over heterogeneous CTI sources [61], and CTI corpora have been organized into agent-native scaffolds for direct consumption by agents [62]. Related efforts parse hybrid system logs into structured templates [63] and translate natural language into first-order logic that symbolic reasoners can consume [64], and documentation optimized as repository-specific playbooks for coding agents [24] brings this view to software. These works share the premise that knowledge should be represented in the form its consumer can use. They differ from S PEC FORGE in how the representation is judged and improved: knowledge graphs, retrieval corpora, and parsers are typically constructed once and evaluated by extraction or answer accuracy, whereas S PEC FORGE treats the knowledge artifact itself as the object of recursive improvement, judges it by the behavior it induces in the consuming agent, and revises it until that behavior is verified correct. 37 L Compute Resources Used 

All evaluations involving proprietary models (e.g., GPT-4o, Gemini-2.5-Flash, Gemini-3.1-Pro, Claude-4.5-Sonnet), were conducted through the APIs. These calls were issued from standard desktop machines using CPU-only execution, with no reliance on local GPU hardware, which makes the approach easy to reproduce in widely available computing environments. For open-source models (e.g., Qwen), inference was run on a single node equipped with eight NVIDIA H100 GPUs (80 GB each). Experiments were executed sequentially on this node to maintain consistent and reproducible runtime conditions across different model families. Overall, this setup highlights the modest computational demands of our method and shows that our approach remains practical and scalable even in resource-constrained settings when hosted APIs are used. 

M Use of LLMs 

In this work, large language models (LLMs) were primarily used for inference in the specification generation experiments. Specifically, they were employed to generate responses under different prompting and evaluation settings, which enabled us to assess the effectiveness of our method across a range of generation tasks and model families. In addition to their role in experimental inference, LLMs were also used as a writing assistant during manuscript preparation. In particular, they helped improve the clarity, fluency, and overall readability of the paper by polishing sentence-level expressions and refining the presentation of technical descriptions. All substantive technical content, experimental design, analysis, and conclusions were determined and verified by the authors. 

N Limitations 

The recursion in S PEC FORGE is over specifications, not over the improver: the search procedure itself is fixed, and the loop requires a reference implementation against which self-generated tests are validated. Our evaluation of the loop covers 20 Python modules; other languages appear only as a downstream target in the cross-language transfer experiment (§4.5.1). 

O Broader Impact 

This work studies how a coding agent can improve the behavioral specifications in its harness: natural-language descriptions of program behavior that are written for code-generation models and verified by execution, in contrast to human-facing documentation. Its main potential benefit is to improve the reliability, controllability, and practical utility of LLM-based coding agents in tasks such as code synthesis, migration, translation, and feature development, thereby reducing iteration cost and improving software quality. At the same time, more effective autonomous coding systems may lower the barrier to producing software at scale, including in harmful settings. The self-improvement studied here is bounded by design: it changes neither model weights nor the search procedure, and every candidate revision is evaluated by execution against tests validated on the reference implementation. Our method does not remove the need for verification or human oversight; it operates entirely through test-based feedback and does not introduce capabilities beyond improving the behavioral precision of specifications for downstream code generation. We therefore view its societal implications as broadly aligned with those of existing LLM-based software engineering systems, with the main positive contribution being better-structured, more evaluable interaction between codebases and generative models. 38 NeurIPS Paper Checklist
