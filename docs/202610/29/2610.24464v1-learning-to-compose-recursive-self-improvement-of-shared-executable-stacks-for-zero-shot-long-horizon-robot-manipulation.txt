ABSTRACT 

Individually competent robot skills can fail when composed: tools may lack a required capability, completion signals may misrepresent physical progress, and one skill may leave a state that violates its successor’s prerequisites. We introduce Recursia, a recursive self-improvement framework that treats the shared executable stack, rather than individual task programs, as the persistent unit of improvement. The stack integrates tools, skills with execution contracts, handoffs, and verifiers. Source-side execution traces guide failure attribution and the generation of missing tools or repairs to existing shared components. Generality checks, mechanism tests, and paired selection and regression gates determine which changes become the next parent. The resulting stack is frozen and reused through declarative task adapters, allowing source-derived changes to support new compositions without target-side code repair. Experiments cover LIBERO-Pro Long simulation and a physical Franka FR3 equipped with a Franka Hand. In simulation, Recursia improves success over ASPIRE by 5.8 percentage points under Pos perturbations and 15.1 points under Task 

perturbations. Across three physical compositional target tasks, it improves mean success over the Skill Document Only baseline by 40 percentage points. Analyses of constituent execution, candidate rejection, and inference drivers distinguish local mechanism improvements from complete task success and characterize the cost of feedback-conditioned orchestration. These results examine shared executable interfaces as a concrete mechanism for compositional transfer in robot programming. 

1 Introduction 

Long-horizon robot manipulation demands more than a repertoire of individually capable skills (Mees et al., 2021). Executing a pick-and-place action, for instance, is insufficient if it leaves the environment in a state that violates the preconditions of the subsequent skill (Xu et al., 2026). Grounding high-level language plans in skill affordances and perceptual geometry is therefore critical for physically feasible execution (Ahn et al., 2022; Huang et al., 2023). The central question is how skills acquired on source tasks can be composed to reliably solve previously unseen long-horizon target tasks. Coding agents provide a natural testbed for studying this compositional generalization (Liang et al., 2023; Mu et al., 2024; Fu et al., 2026). Language-model-generated programs can invoke perception and control

APIs, implement feedback loops, and reuse procedural abstractions (Liang et al., 2023). RoboCodeX further decomposes multimodal instructions into object-centric manipulation units and synthesizes control code (Mu et al., 2024), while ProgPrompt incorporates state-feedback assertions and recovery actions into generated plans (Singh et al., 2023). Skill-library systems such as Voyager store executable procedures and use environmental feedback for extension (Wang et al., 2023); ASPIRE combines execution feedback, program refinement, skill discovery, and evolutionary search for manipulation (Lu et al., 2026). Lifelong Robot Library Learning expands skill repertoires from accumulated experience (Tziafas and Kasaei, 2024), and Uni-Skill requests new skill implementations when existing ones fall short (Xie et al., 2026). CaP-X examines how abstraction levels, perceptual grounding, and structured execution feedback affect the reliability of embodied coding agents (Fu et al., 2026). Although these capabilities make program improvement a promising route to transfer, reliable composition depends not only on the generated task program, but critically on the shared interfaces it invokes: tools, skill contracts, inter-skill state transfers, and verification logic. Thus, the central object of study shifts from how an agent writes a program to which reusable execution semantics that program inherits. We identify four key obstacles to reliable composition: (1) Tool insufficiency , where a task requires a reusable capability absent from the initial API; (2) Semantic misalignment , where an existing tool returns normally despite failing to reach its requested pose of the next tool in the skill; (3) State incompatibility ,where a skill’s terminal state violates its successor’s preconditions (Xu et al., 2026); and (4) Verification brittleness , where incorrect checks advance an unfinished task or disturb a completed goal. These failure modes correspond to different interfaces in a hierarchical controller: tool execution, skill completion, inter-skill state transfer, and verifiers. Prior systems acquire and reuse executable skills from experience (Wang et al., 2023; Tziafas and Kasaei, 2024; Lu et al., 2026), and execution-guided self-debugging demonstrates that failed programs yield useful repair evidence (Chen et al., 2024). The Darwin Gödel Machine extends this to persistent self-modification evaluated on coding benchmarks (Zhang et al., 2025). We investigate how repairs to shared interfaces with multiple layers can be validated and retained across tasks. We hypothesize that a repair at a shared interface should improve multiple compositions, whereas a task-specific patch should benefit only the trajectory in which it is written. We examine this hypothesis through simulation and physical-robot experiments on long-horizon compositions. We propose Recursia, a framework that targets compositional generalization by treating the shared executable stack as the primary object of persistent improvement. A coding agent can add missing tools, repair skill contracts, or improve handoffs and verifiers. Each modification becomes part of a versioned implementation reused by subsequent source tasks and frozen during target-task execution. Specifically, Recursia is stack-aware and validation-gated. Source-side execution traces identify the first violated requirement, attributing failures to specific repair layers. This attribution proposes a mechanism for change but does not itself establish efficacy. Candidates must satisfy restrictions on task-specific specialization, survive paired comparisons with the parent stack, and pass the validation gate with selection gate and regression gate. Accepted changes are retained with their failure class, validation evidence, and code version. Task variation is expressed through declarative adapters. At deployment, the frozen stack relies solely on permitted robot observations; evaluator-side ground truth used during source diagnosis is never an input to the deployed policy. Our contributions are threefold: (1) We formulate skill composition as the persistent improvement of a shared executable stack integrating tools, skills with execution contracts, handoffs, and verifiers, and enable the generation of previously absent tools. (2) We introduce a failure-attributed improvement procedure that localizes repairs to specific stack layers and validates shared patches through generality and regression gates. (3) We evaluate frozen-stack transfer to long-horizon compositions in LIBERO-Pro Long simulation and on a physical Franka FR3 robot, comparing with skill-library and skill-document baselines and analyzing compositional execution, validation decisions, and inference strategies.

Sk = ( Tk, Kk, Hk, Vk), (1) where Tk contains tools, Kk reusable skills, Hk handoff mechanisms, and Vk verifier mechanisms. Learning and debugging occurs through changes and modifications to executable code; the foundation model is held fixed within a comparison. The declarative adapter aτ provides object descriptions, support or destination descriptions, relation types, and goal dependencies. A shared executor composes calls to these components using aτ and the available observation history ht = ( o0, u 0, . . . , o t).We use zero-shot compositional transfer to mean that target-task compositions do not provide feedback for stack modification, and the frozen stack is executed without target-specific code repair. Source and target tasks may share objects, relations, or individual skills. 

2.2 Four-layer Shared Executable Stack Tool. Tools expose reusable perception, geometry, planning, or execution operations. Their interfaces specify inputs, coordinate conventions, observable completion conditions, and resource limits. The tool set is extensible. When an attributed source failure reveals that no available operation can satisfy a required capability, the agent proposes a new shared tool rather than embedding a task-specific workaround in the adapter. A proposal defines the missing capability, an interface, the permitted observations it consumes, and tests of its intended behavior. New tools are assembled from the permitted lower-level operations and are registered only after validation. Tool generation cannot introduce privileged sensing at deployment or alter the external evaluator. We distinguish these additions from repairs to existing tools in the experimental analysis. Figure 2 illustrates representative interfaces.

where Pre i defines observable prerequisites, πi is a parameterized program, Post i specifies evidence required at completion, and Bi bounds resource use. Preconditions and postconditions refer to task arguments and measured geometry, not identities of benchmark tasks. Execution returns evidence and a reason for termination, allowing the caller to distinguish a completed motion from an established task relation. Contracts are executable checks, not formal guarantees of correctness in unobserved states. 

Handoff. The completion of one skill does not imply readiness for the next: 

Post i(ht)̸ ⇒ Pre i+1 (ht). (3) A handoff updates the state used by the successor, checks its prerequisites, and checks previously achieved relations that later actions could disturb. Depending on the observed failure, the shared executor may re-observe, invoke a bounded recovery, or stop. Recovery must establish the missing prerequisite before execution resumes. For instance, a completed release motion requires a subsequent retreat before the next grasp becomes executable. The handoff makes this transition explicit. 

Verifier. The verification layer evaluates object identity and task-relevant relations from permitted observations and execution history. The external evaluator independently measures its errors; the internal evaluator’s own output is never used as the ground-truth success label. The external evaluator’s role is distinct from a motion tool’s arrival check: reaching a pose does not establish that the intended object is supported by the intended surface. The external verification uses support geometry and object identity across observations to decide whether the evidence permits advancement or recovery. Together, these levels define the unit of reuse. A validated tool can serve several skills, a skill can appear in several goal sequences, and a handoff or relation check can apply across tasks. Figure 2 shows four representative shared interfaces. The layers group responsibilities within one executable stack. 

2.3 Failure-Attributed Improvement Procedure 

The executor run source rollouts and records actions, observations and robot state. Source diagnosis use simulator ground truth to distinguish failure mechanisms, while the deployed stack remains restricted to permitted observations. The attribution procedure identifies the earliest supported violation of an execution requirement and records its stage, evidence, and affected component. It distinguishes an absent capability from an incorrectly implemented one. The coding agent receives this evidence and proposes a candidate modification δ. The proposal names the failure class, the stack level to modify, the intended repair, and the tests that would evaluate the repair. Examples in Figure 2 include adding a missing constrained-motion operation, preventing unexecuted planning candidates from changing later solves, or revising a handoff that starts its successor before transport has completed. The candidate repair modify an existing component of Sk = ( Tk, Kk, Hk, Vk) or extend the inventory. For instance, the candidate repair can extend the tool inventory as follows: 

S′ = Apply( Sk, δ ), T ′ = Tk ∪ { tnew } for an accepted tool addition . (4) At each improvement iteration, the agent selects one shared-module slot for modification. Candidate changes are confined to that slot. For example, when the shared-tool slot is selected, the other shared components, diagnostic procedures, retrieval, search code, and data splits remain fixed during that iteration. First-failure attribution guides where to intervene, while the mechanism tests and paired execution determine whether that intervention works. Recursia also allows the strategy update to change across iterations. 2.4 Multidimensional Validation Gate 

Candidate acceptance combines three types of evidence. Firstly, generality checks reject benchmark-specific specialization in shared code, including task or seed identifiers and object- or scene-specific control branches. Geometric constants require a documented source, such as robot calibration, measured geometry, or a declared object-independent construction. Secondly, mechanism tests check the proposed behavior before broader execution. Perception and verification patches can be replayed on recorded observations. Motion patches require execution tests, because an old trajectory does not reveal what a new controller would do. Tests also check interface compatibility and whether downstream actions respect failure returns. A newly generated tool must demonstrate both its intended capability and bounded handling of unsupported requests. Finally, parent and candidate are compared on identical source-task states under a resource policy fixed before candidate evaluation in the current iteration. Let G(δ) indicate the generality checks, U (δ) the mechanism tests, and R(S′, Sk; Dsel , B ) the paired performance and regression gate. Acceptance is 

Accept( δ) = G(δ) ∧ U (δ) ∧ R(S′, Sk; Dsel , B ). (5)

3 Experiments 

Our experiments examine whether source-side improvement of a shared executable stack transfers to unseen long-horizon compositions and which levels of the shared stack contribute to transfer. 

3.1 Experimental Setup Setup. We use LIBERO-90 (Liu et al., 2023) for debugging, including failure diagnosis, repair generation, and candidate selection. Improvements persist in a versioned executable stack rather than in target-specific programs. All source-side development is completed before target evaluation, and the selected stack is frozen together with its tools, skill implementations, handoff logic, and verifiers. The coding model and its parameters remain fixed within each controlled comparison. The first track evaluates the frozen stack on LIBERO-Pro Long, following the long-horizon transfer setting studied by ASPIRE (Zhou et al., 2025; Lu et al., 2026), with 10 long-horizon tasks evaluated along two axes. Pos changes initial object positions; Task changes the task specification. Each task–axis pair is evaluated on seeds 1–50, yielding 500 episodes per axis. The 10 task names and their axis-specific results are listed in Appendix D. The second track evaluates on a physical Franka FR3 equipped with a Franka Hand. Physical evaluation trajectories are not used for stack repair or selection.

3.4 Analysis of Compositional Generalization 

The Recursia framework targets compositional generalization, combining knowledge from multiple source tasks to enable zero-shot transfer to long-horizon target tasks. This subsection aims to demonstrate this capability through retrospective case studies. Compositional transfer requires both competent constituent skills and compatible states at their boundaries. To disentangle improvements in individual skills from those in compositional ability, we examine this distinction through retrospective execution cases, separating two events: completion of the predecessor’s goal and establishment of the successor’s prerequisites. In particular, while the predecessor task is complete in the current state, this does not guarantee that the next object can be readily identified, reached, or manipulated. A useful diagnostic is the difference between isolated and chained success: 

∆chain = pisolated success − pchained success (6) This quantity measures sensitivity induced by composition capability. 

Improving isolated skills does not remove the downstream bottleneck. At N = 11 , the standalone stove-on operation improved from 0/10 to 10 /10 on both development and selection datasets, whereas the stove-pan composition remained 0/10 . In the inspected development rollouts, the stove-on predicate became True , but subsequent manipulation lost the pan after a grasp attempt; alternative candidates were also rejected as outside the inverse-kinematics workspace. Thus, the rotary repair improved the first operation without establishing the conditions needed to complete the second. This comparison locates the remaining bottleneck and shows the difference between isolated and chained success. Our approach filled this gap by handoff repair mechanism, in the later iterations. 

Relational success and successor readiness are distinct. In the N = 6 mug-pudding sequence, the mug-on-plate predicate became True in all ten Pos episodes, while the full conjunction succeeded in only one. In seed 42, the mug goal became True at step 573 and remained True , but subsequent pudding binding returned not_found . Seed 41 provides a successful contrast: the mug goal became True at step 552 and the pudding goal at step 1440, with the first goal preserved (Figure 4). A drawer sequence exhibits the same failure structure: seed 48 achieved bowl containment, but closing stopped at part_not_found . These traces identify perceptual binding as a prerequisite that is not certified by predecessor goal completion. Together, these cases distinguish failures of successor execution from failures to establish successor readiness. 3.5 Analysis of Inference Methods 

All inference methods are driven by declarative adapters. We compare three inference drivers over the same frozen shared stack: rule-based driver, one-shot task-program driver, and online closed-loop driver. These drivers differ in how high-level execution decisions are specified and updated. The rule-based driver follows predefined decision rules. The one-shot task-program driver executes an initially generated program, which may include observation-dependent branches and bounded retries. The online closed-loop 2 driver conditions subsequent decisions on observations and execution outcomes throughout the episode. All three may use observation feedback and closed-loop low-level control. The results are shown in Figure 5. One-shot generation describes the lifetime of the program, rather than an absence of feedback during its execution. In ASPIRE’s zero-shot setting, task-program generation excludes target-side debugging, but the one-shot generated program may still re-observe the scene and use closed-loop low-level control (Lu et al., 2026). Here, we use the frozen shared stack.

3.6 Analysis of the Validation Gate 

The Recursia framework incorporates two critical validation components for the validation gate, i.e., the selection gate and the regression gate , to address two distinct risks: a candidate may correct a local mechanism without improving overall task completion (mitigated by the selection gate), or improve aggregate completion while disrupting previously successful states (mitigated by the regression gate). This subsection uses retrospective case studies to demonstrate their effectiveness. In the book-transfer task, the development summary reported candidate-filter rejection in eight of ten episodes for early iterations 

N = 8 . 4 Related Work 

Embodied Agents. Language-guided robot agents connect high-level reasoning to physical execution through learned action models or executable programs. Vision-language-action models (VLA) such as RT-2, OpenVLA, and π series map visual observations and language instructions to robot actions (Brohan et al., 2023; Kim et al., 2024; Black et al., 2025). Programmatic approaches instead express control through calls to perception and action interfaces. Code as Policies composes these calls into robot programs and recursively generates missing helper functions (Liang et al., 2023), while ProgPrompt grounds plan generation in programmatic descriptions of available actions and objects (Singh et al., 2023). CaP-X extends this setting with systematic evaluation of coding agents, structured execution feedback, and automatic skill synthesis (Fu et al., 2026). Together, these approaches provide the building blocks for language-guided manipulation. Recursia focuses on how those building blocks improve across tasks: it persistently modifies the shared tools, skills, handoffs, and verifiers that generated programs invoke. 

Embodied Recursive Self-Improvement. A central question in recursive self-improving agents is where experienc and knowledge is retained and how it changes subsequent behavior. The Darwin Gödel Machine retains improvements in the agent’s own code and evaluates successive variants on coding benchmarks (Zhang et al., 2025). In robotics, Eureka uses language models to generate reward functions for policy learning (Ma et al., 2024), while evolutionary code search directly synthesizes executable control policies (Guo et al., 2026). Skill-library approaches retain experience as reusable procedures. Voyager accumulates executable skills in Minecraft (Wang et al., 2023); Lifelong Robot Library Learning bootstraps composable skills for robot control (Tziafas and Kasaei, 2024); and Uni-Skill requests new implementations when its existing repository cannot support a plan (Xie et al., 2026). These approaches make accumulated experience available to later tasks through improved policies, programs, or skill repertoires. ASPIRE (Lu et al., 2026) brings execution-driven repair and skill accumulation into a continual robot-programming loop. It uses execution traces to diagnose failures, distills validated fixes into a transferable skill library. Its evaluation includes transfer to unseen long-horizon tasks, making it the closest precursor to Recursia. Zero-shot transfer is also studied in the context of lifelong learning ( ?), where a robot learns to perform new tasks without additional training. Recursia differs from these approaches by focusing on the shared executable stack as the unit of improvement, allowing for more systematic and reusable repairs across tasks. 

Compositional Generalization for Robotics. Compositional generalization requires familiar capabilities to remain effective when objects, goals, or action sequences are combined in new ways. CLIPort studies language-conditioned manipulation through semantic and spatial abstractions (Shridhar et al., 2021), and  

> 12 Learning to Compose Recursia

VIMA evaluates progressively more novel combinations of task components (Jiang et al., 2022). At longer horizons, CALVIN evaluates sequences of language-conditioned manipulation tasks (Mees et al., 2021), while LIBERO studies knowledge transfer across spatial, object, goal, and task variations (Liu et al., 2023). LIBERO-PRO adds perturbations to initial object positions and task specifications (Zhou et al., 2025). These evaluation settings expose several dimensions of transfer, from recognizing a new combination of familiar concepts to executing a sequence under changed conditions. Reliable sequence execution also depends on the states passed between skills. BATON addresses this dependency by exploring subtasks separately and storing transition-aware memory: verification checks readiness, handoff restoration repairs entry conditions, and lookahead favors outcomes that the next subtask can use (Xu et al., 2026). Its treatment of transitions makes explicit why a skill can succeed in isolation yet fail as part of a chain. Recursia places this dependency within a broader stack-improvement problem. Handoff repairs are validated alongside changes to tools, skill contracts, and verification, and their shared implementations are reused unchanged on target compositions. Our evaluation therefore examines both the competence of individual skills and the reliability of their composition, tracing transfer to source-side changes in the executable stack. 

5 Limitations and Conclusion 

Our evaluation has several limitations. First, source-side ground-truth diagnosis provides information that may not be available on a physical robot. In simulation, failed episodes can be reset to a controlled initial state and replayed repeatedly. On a physical robot, resetting the scene can be slow, unsafe, or impossible after an object has moved, and the diagnostic evidence needed to identify the first violated requirement is often incomplete or expensive to obtain. Deployment does not consume simulator ground truth, but transferring the improvement procedure itself to real hardware therefore requires reliable alternatives, such as calibrated state logging, external sensing, human annotations, or conservative uncertainty handling. Second, we have not evaluated cross-embodiment generalization. All source and target experiments use the same robot embodiment and execution interfaces. A shared repair may depend on kinematics, gripper geometry, controller conventions, or calibration details, so transfer across robot platforms remains untested. We present a framework for improving the shared executable mechanisms through which coding agents compose robot skills. The stack can grow when a required tool is missing and change when existing tools, contracts, handoffs, or verification fail. Source failure attribution directs these changes, while validation gates determine which changes persist. Frozen reuse then connects a source-side modification to the code executed in an unseen long-horizon composition. The primary LIBERO-Pro Long results are 28.4% on

C.1 Grasping-backend Mismatch 

Our simulation experiments use the open-source Contact-GraspNet backend rather than the AnyGraspFang et al. (2023) backend used in the ASPIRE configuration considered for comparison. This mismatch limits the fairness of a direct performance comparison, because differences in grasp proposal quality may affect both individual manipulation outcomes and long-horizon task completion. We speculate that replacing Contact-GraspNet (Sundermeyer et al., 2021) with AnyGrasp could improve grasp-dependent execution; this effect has not been measured in a matched backend comparison.

C.3 Regression Gates 

Candidate construction checks exact patch anchors, the declared shared module, forbidden literals in inserted code, Python compilation, and supplied test files. Identifier checks constrain explicit specialization to benchmark tasks or seeds. These automated checks do not establish semantic generality; review additionally examines whether geometric constants follow calibration, measured geometry, or an object-independent construction. Missing tests produce a warning in the inherited builder, while the evaluation protocol requires supporting tests before acceptance. Mechanism tests exercise the changed behavior and its failure returns. Recorded observations support replay of perception and verification decisions; changes to motion require execution evidence. Parent and candidate are then run from matched source initial states. The gate configuration is fixed at the beginning of each RSI iteration and specifies the evaluation stages, development and selection panels, regression tasks, required improvements, paired-loss limits, and integrity and timeout checks. These settings can evolve across iterations, but are held fixed for all candidate comparisons within a given iteration. The rollout manifest records the corresponding seed-to-state mapping and resource budgets. Numeric acceptance is followed by inspection of newly successful trajectories and new regression failures. The parent changes only after the checks and review required by the current iteration pass; otherwise the frozen parent is retained. Selection and regression outcomes used by this gate are acceptance evidence, not an independent audit. Any audit panel must be excluded from proposal generation and candidate selection, and reported separately. Target episodes do not supply evidence to the source acceptance gate. 

C.4 Source–Target Combination Generalization 

Source tasks provide manipulation constituents such as grasping, transport, support placement, relative placement, and articulated-object actuation. Target instructions combine these constituents into longer goal sequences. Representative compositions include stove activation followed by pan placement, mug placement followed by pudding placement beside a plate, and bowl containment followed by drawer closure. Object phrases specify the manipulated object and reference; relation types distinguish the required goal; ordered subgoals specify the composition.
