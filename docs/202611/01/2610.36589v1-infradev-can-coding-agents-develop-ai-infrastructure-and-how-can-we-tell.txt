# Abstract 

Coding agents are beginning to develop the production-grade AI infrastructure that trains and serves large models, yet existing benchmarks cover only single kernels or single-GPU tasks, and grade with tests and prompts that misjudge both correct and incorrect patches. We introduce InfraDev, a benchmark of 36 tasks built from real-world pull requests to Megatron-LM, vLLM, and verl, covering infrastructure development for training, infer-ence, and reinforcement learning. Each task asks an agent to reimplement a real change that spans many files and must run correctly across many GPUs. To grade such changes, we jointly synthesize hidden probes, which enforce the requirements the original tests leave unchecked, and a prompt that states every interface the probes call without revealing the solution. We also design a shared execution environment that reuses dependencies and artifacts across tasks, cutting storage by 52–57% and build time by 13–14% on Megatron-LM and vLLM. Across six frontier models, the best resolves only 38.9% of the tasks; the probes reject 32% of the submissions that pass every official test, and with the original pull request descriptions as prompts, no model resolves a single task. Failure analysis shows that structural and state errors dominate and that agents’ own tests rarely check memory, time, or traffic. Turning these findings into an agent skill raises the resolved rate of a frontier model on the Megatron-LM tasks by 10.5%. 

# 1 Introduction 

Real-world AI infrastructure spans training, inference, and reinforcement learning (Shoeybi et al., 2020; Kwon et al., 2023; Zheng et al., 2024; Sheng et al., 2025). Each is backed by a large codebase that evolves rapidly with new models and hardware: vLLM alone merged 1,918 commits in June 2026, about 64 per day (Luu, 2026). Developing this infrastructure means implementing changes that range from a single GPU kernel to coordinated edits across parallelism, memory, and communication subsystems. Such a change must be correct in two senses. It must be numerically correct , computing the right activations, gradients, and states under distributed execution, and it must be behaviorally correct : a new feature must take effect, and an optimization must actually reduce memory, communication, or time on realistic workloads. Coding agents are beginning to make these changes, as they take on longer and more complex software engineering tasks (Jimenez et al., 2024; Yang et al., 2024; Wang et al., 2025b; Deng et al., 2025; Kwa et al., 2025). This raises the question: Can coding agents develop real-world AI infrastructure, and how can we tell? 

Answering this question requires benchmarks that address three limitations of existing evaluations. First, existing benchmarks have a narrow task scope . Most evaluate individual GPU kernels (Ouyang et al., 2025; Li et al., 2025; Chan et al., 2026; Huang et al., 2026) or single-GPU inference optimization (Nangia et al., 2026; Yeon et al., 2026). Φ-Bench recently extended the scope to system-level optimization (Ding et al., 2026), but its tasks are optimization problems with fixed targets rather than the changes developers actually ship. Most real infrastructure changes go further: they span many files and modules and must run correctly across many GPUs. Second, reusing a pull request’s own tests and description as the grading suite and task

Among the 36 pull requests we study, 24 have no test that checks a numerical result, and 13 of the 15 performance optimizations have no test that checks the promised saving, so a patch that skips the optimization still passes. Each task pins its own dependencies and needs large artifacts such as model weights. Preparing them separately for every task takes substantial storage and time, which limits how many tasks a benchmark can afford and who can run it. We address these limitations with three contributions, and then use the resulting benchmark to understand why agents fail and to improve them. 

A benchmark of large-scale AI infrastructure tasks. InfraDev contains 36 carefully selected tasks built from merged pull requests to Megatron-LM, vLLM, and verl, covering training, inference, and reinforcement learning. We start from the 21,389 pull requests merged into these repositories between January 2025 and September 2026. We keep those that change core functionality, touch multiple files, add tests, and exceed 1,000 lines. Each remaining task asks an agent to reimplement one pull request. A task changes 17.4 files and 1,818 lines on average, and 20 of the 36 require multiple GPUs to run. 

A method that builds tests and prompts together. We propose hidden-probe synthesis, implemented as an agent. For each selected pull request, the agent first writes adversarial patches that pass the official tests but violate requirements the tests leave unchecked. It then writes new tests for these requirements, which we call hidden probes . A probe is kept only if it passes an acceptance check: it must accept the golden patch in repeated runs and reject the pre-PR snapshot, every adversarial patch, and a hollow patch that defines the new interfaces without implementing them. Finally, the agent writes a prompt that states every behavior the probes check and every interface they call, without revealing how to implement them. Both halves are necessary: the probes reject 32% of the submissions that pass all official tests, and with the original pull request descriptions as prompts, no model resolves a single task. 

A resource-efficient execution environment. We design an execution environment that installs each task’s dependencies into a virtual environment on a shared volume and allows tasks to share overlapping depen-dencies directly. Model weights and datasets are likewise stored once in a shared cache and reused across tasks. This cuts storage by 52–57% and environment build time by 13–14% on Megatron-LM and vLLM, compared with building one image per task as prior benchmarks do (Nangia et al., 2026; Yeon et al., 2026). Using InfraDev, we evaluate six frontier coding agents. The best, GPT-6 Sol, resolves only 38.9% of the tasks (Section 4.2). We then analyze the 1,754 failing test cases of the graded submissions and find failure modes that agents repeat: structural errors are the most common, state errors often escape the official tests, the tests agents write for themselves rarely check memory, time, or traffic, and two thirds of the errors are shared by most models. Finally, we encode these findings as an agent skill for AI infrastructure development . The skill summa-rizes the failure cases and incorporate several development principles revealed by InfraDev. Our experiments show that this skill raise the resolved rate of GPT-5.6 Sol on the Megatron-LM tasks from 42.1% to 52.6%, where the failure modes it targets are most common (Section 4.5). Encouraged by the above results, we will open-source InfraDev and believe it offers a foundation for mea-suring and improving coding agents on large-scale AI infrastructure. 

# 2 Related Work 

Benchmarks for AI infrastructure and ML engineering. Most benchmarks in this area evaluate GPU kernel generation and optimization (Ouyang et al., 2025; Li et al., 2025; Xing et al., 2026; Lange et al., 2025), extended to multiple GPUs by ParallelKernelBench (Chan et al., 2026) and to kernels inside their host frameworks by RealisticTritonBench (Huang et al., 2026). ISO-Bench, InferenceBench, and Φ-Bench move up to inference optimization, but on a single GPU and with optimization targets fixed in advance (Nangia et al., 2026; Yeon et al., 2026; Ding et al., 2026). A separate line evaluates agents on ML engineering, such as training models for Kaggle competitions or reproducing papers (Chan et al., 2025; Starace et al., 2025; Wijk et al., 2025); there the agent uses infrastructure rather than changing it. InfraDev differs from all of these in its unit of work: a merged pull request to a production training, inference, or RL framework, which typically changes many files and must run correctly across GPUs. 

Grading in repository-level benchmarks. SWE-bench and its descendants grade a patch with the tests that shipped with the original pull request (Jimenez et al., 2024; Zan et al., 2025; Deng et al., 2025), and infrastructure benchmarks extend them only with end-to-end checks of accuracy and speed (Nangia et al., 2026; Huang et al., 2026). Both weaknesses of this recipe are known. On the test side, UTBoost adds tests to raise coverage (Yu et al., 2025), SWE-ABS uses adversarial patches to show that many accepted patches are wrong (Yu et al., 2026), and work on verifiable rewards reports policies that learn to pass weak tests with-out solving the task (Baker et al., 2025). On the prompt side, SWE-bench Verified removes underspecified tasks by human annotation (Chowdhury et al., 2024) and SWE-Bench Pro adds requirement and interface lists (Deng et al., 2025). Each fixes one side. InfraDev fixes both in one loop: adversarial patches find requirements the official tests miss, hidden probes enforce them, and the prompt is rewritten to state every interface the probes depend on (§3.1.2). Environment reuse is a smaller but practical concern: prior bench-marks build one image per task (Jimenez et al., 2024; Nangia et al., 2026) or share only a base image (Huang et al., 2026); we share dependency environments and artifact caches across tasks (§3.3). 

Understanding and improving coding agents. Failure analyses of agents on SWE-bench and related benchmarks report where runs break down, and agents are improved by better interfaces (Yang et al., 2024), reusable skills and tool libraries, or reflection over past attempts. Kernel-generation systems apply the same ideas to one task type (Lange et al., 2025; Wang et al., 2025a; Baronio et al., 2026). Our skill differs in where it comes from: it encodes the three failure classes, contains no task-specific answers, and targets the checks that agents skip, such as callers of a changed function and the resource a change promises to save. 

# 3 InfraDev 

Each task in InfraDev asks a coding agent to reimplement a real merged PR (pull request) from an AI in-frastructure project. Figure 1 shows how we build and evaluate these tasks. We first curate challenging PRs that change core functionality of Megatron-LM, verl, and vLLM (§3.1). For each PR, we jointly synthesize the tests and the prompt of the task. An agent adds hidden probes that reject shortcut implementations of the PR. Another agent writes a prompt that states what these tests check without revealing the solution (§3.1.2). The agent under evaluation then implements the task in a multi-GPU sandbox, based on the prompt and the repository snapshot just before the PR. We grade its patch with the official tests of the PR and the hidden probes (§3.2). ## 3.1 Task Construction  

> 3.1.1 PR Curation

We collect tasks from three widely used production repositories that together cover the model life cycle: Megatron-LM for training (Shoeybi et al., 2020), verl for reinforcement learning (Sheng et al., 2025), and vLLM for inference (Kwon et al., 2023). We apply rule-based filters to all of their PRs and keep those that are merged and not reverted, change at least 1,000 lines, and add new tests. Guided by domain expertise, we then manually select the PRs that concern the core functionality of each framework. This yields 36 PRs, most of which add new features or optimize performance (Table 1). For each PR, we record the pre-PR snapshot just before the merge and the post-PR snapshot right after it. Their difference is the golden patch , the change the developers actually made, which serves as the reference solution.  

> 3.1.2 Joint Synthesis of Tests and Prompt

Hidden-probe synthesis. We judge whether a modification completes a task by two criteria. Behavioral correctness means that the program behaves as the task requires when it runs: a new feature must take effect, and an optimization must actually reduce memory, communication, or time. Numerical correctness means that the program computes the right values, such as activations, gradients, and model parameters. The official tests of the selected PRs are weak in both criteria. First, numerical checks are often absent: in 24 of the 36 evaluated tasks, no official assertion verifies the numerical result of the modification. Second, behavioral checks are rare: in 13 of the 15 PRs that optimize performance, the official tests never check whether the optimization saves time, memory, or communication. An implementation that computes the right output but omits the optimization therefore still passes them. We address this gap with an agent skill that iteratively synthesizes hidden probes , tests for requirements that a task imposes but its official tests leave unchecked (Algorithm 1). The agent first summarizes what the PR promises to implement (line 1). It then builds adversarial patches , incorrect implementations that pass every official test but violate numerical or behavioral correctness (line 2). Next, the agent writes probes that check both criteria (line 3). Appendix A.1 describes how a probe decides whether a result is correct. For example, verl PR 6974 syncs weights from the trainer to the rollout engine by sending only the entries that changed since the last step. Its probe counts the sent entries and rejects an adversarial patch that sends 65,536 entries when only 655 have changed. We then refine the probes and the adversarial patches together (lines 4–5). In each round, the skill runs a check, and the agent revises every probe or adversarial patch that fails. The check requires each probe to pass on the golden patch and fail on every adversarial patch. It also requires each adversarial patch to break a promise of the PR while still passing the official tests. Appendix A.1 lists the full check. 

Prompt synthesis. To improve the quality of prompts, we rewrite each PR as a task prompt, the agent’s only description of the change. The prompt must be sufficient : a correct implementation must not fail because the prompt omits an interface or requirement on which the tests depend, such as the name of a function they import. It must also be solution-free : it must not explain how to meet the requirements, because such guidance does part of the task and makes weaker agents appear capable. We meet both requirements by splitting the information about a PR into a specification and a solution and putting only the specification in the prompt. The specification states what the change must do: the interfaces the tests call, the behaviors the official tests and hidden probes check, and the execution rules, such as the definition of done. ## 3.2 Evaluation 

Inference and Grading. We prepare Docker containers for all agents and set a 2.5 hours time limit for each PR. Recovery mechanism is also introduced to prevent agent stopped accidentally in early stage. Agent’s output patch is applied to the pre-PR snapshot in a separate container. The test directory is then replaced by that of the post-PR snapshot for evaluation, so agents cannot cheat by modifying test. To quantitatively evaluate how good agents solve the task, grading will evaluate patches with real GPUs. 

Metrics. We grade each patch on the official tests together with the hidden probes. For a task p, let Np be the number of test cases collected when the golden patch runs, including the cases that the golden patch itself fails or skips on our hardware. The pass rate of a patch is sp = passed p/N p, and % Passed averages sp

equally over tasks. A task is resolved when the patch passes at least as many test cases as the golden patch, so the patch does not have to pass the cases that the golden patch fails. % Resolved is the share of resolved tasks. A missing, empty, or inapplicable patch scores 0/N p instead of being dropped, since dropping it would reward models that give up. Harness faults are excluded and counted separately, so an infrastructure error is never recorded as a model failure. We keep the per-test outcomes and the full agent trace of every run for the failure analysis in §4.4. 

## 3.3 Execution Environment 

Limitation of Docker. Repository-level benchmarks usually build one Docker image per task. Docker caches image builds as a prefix, reusing the build steps before the first changed step and rerunning every step after it. This prefix cache works poorly for AI infrastructure projects, whose dependencies change often. For example, the 19 Megatron-LM tasks were merged within five months but use six versions of Transformer Engine. Each version change makes Docker rerun dependency steps after it. Moreover, tests of production infrastructure need large artifacts, such as model weights and datasets. The test code downloads these artifacts while it runs, so Docker does not see them and cannot cache them across tasks. 

Resource-efficient Execution Environment. We break the prefix reuse of Docker and reuse each package and each artifact independently, so a change to one of them never forces the others to be rebuilt or stored again. We maintain several lightweight base Docker images for each AI infrastructure repository, containing only components shared across multiple PRs, such as CUDA and the Python interpreter. The dependencies of each task go into a virtual environment that uv installs on a volume shared by all containers. ## 4.1 Setup 

Models and harnesses. We evaluate six coding agents on InfraDev, two built on frontier closed-source models and four on open-source models. GPT-6 Sol and GPT-5.6 Sol run in OpenAI’s Codex harness; GLM 5.3, DeepSeek V4 Pro (0813), Kimi K3, and HY4 preview run in the OpenCode harness. 2 We set the reasoning effort of every model to xhigh or a comparable level. Each agent runs once on each task, and we call the patch it produces a submission .

Environment. All experiments run on nodes with eight NVIDIA H800 or H20 GPUs each. Each inference or grading run has exclusive use of one node. An agent has 2.5 hours per task, excluding environment preparation; a run that reaches this limit is graded on the patch it has produced. A task’s golden calibration and the grading of its submissions use the same environment and GPU type.

## 4.3 Ablation Study 

Hidden-probe synthesis. The official tests alone overstate how many tasks agents resolve. We grade every submission twice, on the official tests alone (Set A) and with the hidden probes added (Set B; Figure 2). Adding the hidden probes lowers every model’s resolved rate by 11 to 19 percentage points. Of the 216 submissions, 102 pass all official tests, but only 69 of them also pass the hidden probes. The hidden probes thus reject 32% of the submissions that the official tests accept. 

Prompt synthesis. InfraDev cannot distinguish models without prompt synthesis. We replace the synthesized prompt with the PR’s original description on the Megatron-LM tasks (Figure 3). Once the hidden probes are included, neither GPT-6 Sol nor DeepSeek V4 Pro resolves a single task. Maintaining comprehensive AI infrastructure is hard, and a prompt that omits the required interfaces makes even capable agents fail for reasons unrelated to the task. With the synthesized prompt, the resolved rate is at most 52.6%; the prompt therefore does not hand the agent the implementation. 

Resource-efficient Execution Environment. We compare our execution environment against a baseline that builds one Docker image per task, with each Dockerfile following the task’s official implementation. InfraDev reduces storage by 57% on Megatron-LM, from 80.7 to 34.8 GB, and by 52% on vLLM, from 206.0 to 98.8 GB. The saving grows with the number of tasks: on Megatron-LM, it rises from 17% with two tasks to 57% with all 19, and on vLLM from 27% to 52%. This suggests great scalability as InfraDev expands to more tasks. InfraDev also shortens environment build time by 14% on Megatron-LM and 13% on vLLM.

Structural errors dominate, and state errors often escape official tests. Structural errors are the most common class, found in 48% of the submissions (Figure 4a). Within the class, execution and API errors lead, followed by state and lifecycle errors (Figure 4b). State errors often escape the official tests, which check the result of a single call rather than the state that the call leaves behind. In 15 of the 35 submissions with a state error, only our generated hidden probes catch it. Together, these errors show that models struggle most with changes that span many files of a large repository, where the code must fit the interfaces of many modules and manage state over a long lifetime. 

Numerical errors come from wrong math, not lost precision. All 24 submissions with a numerical error contain an algorithm error, and none fails on precision alone (Figure 4c). The errors are far too large to be rounding noise, so they must come from wrong math rather than from precision lost to differences in hardware or implementation details. On Megatron-LM PR 2440, for example, one patch produces an indexer loss of 19.95 where the loss must be 0.0. Contrary to our own experience as infrastructure developers, where getting the algorithm right is relatively easy and matching numerical precision is the hard part, agents struggle with the algorithm rather than the precision. 

Behavior breaks under execution modes such as CUDA graphs. Of the 51 submissions with a behavioral error, 35 contain an error that appears only under a specific execution mode (Figure 4d). As Figure 5 shows, 60% of the submissions on the four tasks built around CUDA graphs have such an error, compared with 15% on the other tasks. On the CUDA-graph tasks, every such error stays hidden in the default eager mode and appears only once CUDA graphs are turned on. Agents appear to write code for eager mode and treat CUDA graphs as a simple on/off switch, overlooking that a CUDA graph replays recorded GPU work without rerunning the surrounding Python code, so any logic that must run or change on every call is silently skipped. 

Agents rarely test resource requirements like memory, time, or traffic. Agents write their own tests in 94 of the 103 traced runs, but fewer than 2% of the 5,532 assertions check resource usage (Figure 6). Most assertions check functional results (56%) or structure (28%). Of the 11 traced runs that fail a resource check, only one writes any resource assertion. ## 4.5 Improving Agents with Reusable Skills 

Based on our analysis in Section 4.4, we build an agent skill for AI infrastructure development around three principles. • Check every caller and every piece of state the change touches. Structural errors are the most common class. The skill asks the agent to find each caller of a function or class it modifies, keep the signatures, tensor shapes, and dtypes those callers expect, and test stateful objects such as caches and counters over several calls rather than one. • Compare every new computation with a naive reference. Numerical errors all come from wrong algo-rithms. The skill asks the agent to write the formula directly in a few lines of plain PyTorch, compare its code with this reference on small inputs, and check invariants that follow from the math, such as a loss that must be zero or gradients that must be averaged rather than summed across data-parallel ranks. • Test resource requirements and CUDA-graph behavior. Behavioral errors come from resource require-ments and execution modes that agents rarely test. The skill asks the agent to measure peak memory, runtime, or bytes sent before and after its change whenever the task sets a resource requirement, and to rerun its tests with CUDA graphs enabled and check that the outputs match eager mode. The skill contains no task-specific answers or hidden tests. On Megatron-LM tasks, it raises the resolved rate of GPT-5.6 Sol from 42.1% to 52.6%, a gain of 10.5 % points (Figure 7). This suggests that the failure modes exposed by InfraDev can guide agent improvements. However, the remaining gap is still large: closing it will also require advances in training methods, model architectures, and data quality, which InfraDev provides a way to measure. 

# 5 Conclusion and Future Work 

We asked whether coding agents can develop real-world AI infrastructure, and how we can tell. The answer to the first is not yet: the best frontier agent resolves fewer than two in five tasks, and most of its failures are shared by every other agent. For the second, a pull request’s own tests and description are not a reliable judge; grading becomes reliable only when hidden tests and the prompt are written together. The failures are informative. Agents most often write code that does not fit the program around it; when they compute wrong values, the algorithm rather than precision is at fault; and they rarely test whether a change delivers the memory, time, or traffic savings it promises. We propose an agent skill that targets these weaknesses and improve the resolved rate. Two challenges remain in scaling InfraDev. The first is the cost of multi-GPU execution: each agent run occupies an eight-GPU node for up to 2.5 hours, and grading reruns the multi-GPU tests. Evaluating a single model therefore consumes several hundred GPU-hours. Simulation may lower this cost, for example by emulating multiple ranks and their collective communication on fewer GPUs or on CPUs. The second challenge is PR curation, which still relies on domain experts to select every PR by hand. This manual step limits how quickly the benchmark can grow and follow the evolution of its source projects. Automatic methods for identifying suitable PRs would remove this bottleneck. # A Details of Test and Prompt Synthesis 

## A.1 Hidden-Probe Synthesis 

Probe types. A numerical probe compares an output such as a loss, a gradient, or a model state with a reference taken from an existing implementation (Megatron-LM PR 3922 compares the cached Mamba state with a pre-PR path), an invariance (in PR 1989, changing the chunk size must not change the output), a value derived by hand (PR 2440 recomputes the sparse attention in float64 with plain loops), or a property that must always hold (a KL divergence of a distribution from itself is zero). A behavioral probe measures whether the promised effect occurs and compares it with a value derived from the task, such as the bytes that activation offloading moves (PR 1913) or the elements each rank receives (PR 3213). 

Acceptance check. Algorithm 2 gives the check. Besides the pre-PR snapshot and the adversarial patches, every probe must reject a hollow patch , which keeps the interfaces of the golden patch but makes every function added by the PR raise an exception, so that no probe only checks that the new functions exist. The promise that each adversarial patch breaks is recorded by the agent that writes it and is not checked by execution. A PR whose probes do not pass within a fixed number of rounds is left without probes.

# D Failure Analysis: Error Types and Labelling 

Failing test cases. The analysis covers the 36 × 5 = 180 submissions of the five models other than GPT-6 Sol. A failing test case is a test case, from the official tests or the hidden probes, that the golden patch passes and the agent’s output patch does not. We analyze the 1,754 failing test cases and group them by task, test file, error signature, and label each group by reading the failing assertion against the prompt and the submission code. Table 7 counts the submissions with at least one case of each type. 

Structural errors. The code does not fit the program around it. An execution or API error stops the code before any value can be checked: an import or collection failure, a missing symbol, a signature that does not match its callers, or a crash. A shape, layout, or dtype error produces a tensor whose shape, memory layout, or data type differs from what the surrounding code expects. A state or lifecycle error mishandles data that persists across calls, such as caches, buffers, counters, and the ownership of memory, or mishandles the capture and replay of CUDA graphs. 

Behavioral errors. The code computes correct values but misses a requirement of the task. A resource 

error misses a stated requirement on memory, speed, communication traffic, or liveness, such as a peak memory that does not drop or a weight sync that sends more entries than have changed. A condition-specific 

error appears only under a particular condition: a flag, a parallel or CUDA-graph mode, a boundary input, a fallback, or an error path. A numerical mismatch that appears only under such a condition is labelled condition-specific rather than numerical. 

Numerical errors. The code runs and fits the program but computes wrong values. An algorithm error im-plements the wrong computation, such as summing gradients across data-parallel ranks instead of averaging them. A precision-only error implements the right computation with insufficient precision; we assign it only when the same patch passes an exact-logic check. – 19 – InfraDev: Can Coding Agents Develop AI Infrastructure, and How Can We Tell?
